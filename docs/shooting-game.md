# 장애 대응 게임 — 스테이지 작성 규약

`./shoot`는 실제 로컬 MySQL에 장애를 주입하고, 플레이어가 **자기 터미널의 진짜
mysql 클라이언트**로 대응하는 동안 DB 상태와 명령 이력을 감시해 클리어를 판정한다.

읽는 콘텐츠(챕터)와 확인하는 도구(`./exam`)에 이어, **손으로 겪는** 세 번째 축이다.

- 엔진: `scripts/shooting.py` (표준 라이브러리만)
- 랩: `shooting/lab/compose.yaml`
- 스테이지: `shooting/stages/*.json`
- 테스트: `python3 -m unittest discover -s tests`

## 실행

```bash
./shoot doctor          # 사전 점검 (docker / 포트 / 클라이언트 / 스테이지 정의)
./shoot up              # 랩 기동 (최초 1회는 이미지 내려받기로 몇 분)
./shoot --list          # 스테이지 목록
./shoot                 # 스테이지를 골라 플레이
./shoot 1-3-lock-contention
./shoot down            # 랩 정리 (볼륨 포함 — 확인 프롬프트가 뜬다)
```

DB에 접근하는 방법은 두 가지이고, 둘 다 언제든 쓸 수 있다.

- **내장 SQL 콘솔** — 플레이 화면에서 `c`. 창을 오갈 필요가 없다.
- **외부 터미널** — 접속 명령은 게임 화면 상단에 항상 떠 있다.

```bash
MYSQL_PWD=shoot mysql -h127.0.0.1 -P3306 -udba
```

## SQL 콘솔 (`c`)

게임 화면 안에서 바로 질의한다. 상단에 목표 요약줄(`[x][x][ ][ ]`)과 경과 시간이
남아 있어 문맥을 잃지 않고, **콘솔이 열려 있는 동안에도 감시가 계속 돌아가므로**
여기서 장애를 고치면 그 자리에서 클리어된다.

```
1-3-lock-contention  락 지옥  04:12  [x][x][ ][ ]
─────────────────────────────────────────────────
> SELECT COUNT(*) AS waits FROM performance_schema.data_lock_waits
+-------+
| waits |
+-------+
|    36 |
+-------+

> _
Enter 실행   ↑↓ 기록   PgUp/PgDn 스크롤   Esc 돌아가기
```

**판정은 콘솔을 쓰든 외부 터미널을 쓰든 완전히 동일하다.** 판정이 보는 것은
"어디서 쳤는가"가 아니라 "`general_log`에 누구로 기록됐는가"이고, 콘솔도 `dba`
계정으로 접속하기 때문이다. 콘솔만으로 플레이해도 등급·금지 행동 판정이 외부
터미널과 같은 결과가 나오는 것을 검증했다.

### Tab 자동완성

스키마·테이블 이름을 `Tab`으로 완성한다. 셸과 같은 규칙이다 — 후보가 하나면
완성하고, 여럿이면 공통 접두사까지 확장한 뒤 목록을 보여준다.

```
> SELECT * FROM perf⇥
  → SELECT * FROM performance_schema.        (스키마 뒤에 . 을 붙여준다)

> SELECT * FROM performance_schema.data_⇥
  performance_schema.data_lock_waits  performance_schema.data_locks
  → SELECT * FROM performance_schema.data_lock
```

**이 기능이 있는 이유**는 MySQL의 오류 메시지가 사람을 속이기 때문이다.
스키마 이름을 잘못 쓰면 이렇게 답한다:

```
> select * from performence_schema.data_lock_waits;
ERROR 1142 (42000): SELECT command denied to user 'dba'@'localhost'
                    for table 'data_lock_waits'
```

권한은 멀쩡하다. MySQL은 **존재하지 않는 객체도 권한 오류로 답한다**(권한 없는
사용자에게 객체의 존재 여부를 흘리지 않으려는 설계). 이 메시지를 보면 철자가
아니라 `GRANT`를 의심하러 가게 되므로, 오타가 애초에 나지 않게 하는 쪽을 택했다.

이름 목록은 **엔진 경로(`mysql()`)로 가져온다.** `run_player_sql`을 쓰면 자동완성용
질의가 `general_log`에 남아 플레이어가 치지도 않은 명령이 판정 대상에 섞인다.
30초 TTL로 캐시하므로 구축 스테이지에서 새로 만든 객체도 잡힌다.

### 넓은 결과 — 가로 스크롤과 `\G`

`SELECT * FROM performance_schema.data_locks`는 한 줄이 **254칸**이라 화면에 다
들어가지 않는다. 잘렸다는 사실을 알려주고 두 가지 방법을 함께 안내한다.

```
⚠ 행이 254칸으로 화면(78칸)보다 넓습니다.
  Ctrl+F / Ctrl+B 로 좌우로 밀거나, 끝에 \G 를 붙여 세로로 보세요.
```

- **`Ctrl+F` / `Ctrl+B`** — 결과를 20칸씩 좌우로 민다. 화면 아래에
  `◀ 가로 40칸 (폭 254) ▶`로 현재 위치를 보여준다.
- **`\G`** — MySQL 정석. 행을 세로로 펼쳐 전부 읽을 수 있다. 254칸짜리 행은
  가로로 미는 것보다 이쪽이 편하다.

> **왜 하필 `Ctrl+B`/`Ctrl+F`인가.** 콘솔은 `←→`(커서)·`Home/End`·
> `PgUp/PgDn`(세로 스크롤)·`↑↓`(기록)을 이미 쓰고, 인쇄 가능한 문자는 전부 SQL
> 입력으로 들어간다. 남는 건 수식키+화살표뿐인데 그건 **다중 바이트 이스케이프
> 시퀀스**라, Esc 응답성을 위해 낮춰둔 `set_escdelay(25)` 때문에 쪼개져 단독
> Esc로 오해될 수 있다. `Ctrl+<문자>`는 단일 바이트라 항상 도착한다.
> (수식키+`←→`도 보조로 받아주지만 주 키는 아니다.)

### 한계 — 질의마다 새 접속

콘솔은 질의 1회당 새 접속을 쓰는 **무상태** 방식이다. 따라서 다음은 유지되지 않는다:

- `START TRANSACTION` … `COMMIT` (여러 질의에 걸친 트랜잭션)
- `SET SESSION …`, 임시 테이블

이런 작업이 필요하면 외부 터미널을 쓴다. 진단(`SELECT`)과 조치(`KILL`,
`SET GLOBAL`, `CHANGE REPLICATION SOURCE` 등)는 모두 무상태로 문제없이 동작한다.

지속 세션을 지원하려면 `pty`를 띄우고 `mysql>` 프롬프트를 파싱해야 한다 —
`mysql`은 stdout이 tty가 아니면 블록 버퍼링을 해서 단순 파이프로는 교착한다.
사실상 터미널 에뮬레이터 축소판이 필요해 채택하지 않았다.

### 질의 타임아웃 15초

락 인시던트 중에 `UPDATE`를 치면 서버의 `innodb_lock_wait_timeout`(1800초)까지
막힌다. 그대로 두면 TUI가 얼어붙으므로 15초에서 끊고 안내한다.

```
! 질의가 15초를 넘겨 중단했습니다.
  잠금 대기에 막혔을 수 있습니다 — 지금이 바로 그런 상황입니다.
```

막히는 경험 자체가 교보재이므로 숨기지 않는다. 그리고 결과가 2,000줄을 넘으면
표시만 자른다 — 암묵적 `LIMIT`을 붙여 질의 의미를 조용히 바꾸지 않는다.

`exam.py`의 `Esc 닫기(임시저장)` 규약과 같다. 닫아도 목표는 `[?]`로 남고 `r`로
다시 열면 이어서 답할 수 있다. 주관식에서 `b`/`q`를 나가는 키로 쓸 수 없는 이유는
모든 인쇄 가능 문자가 입력값이기 때문이다.

터미널이 실제로 어떤 값을 보내는지 확인해야 하면 `./exam --keydebug`를 쓴다.
두 러너가 같은 `scripts/tui.py` 키 코드를 공유하므로 결과가 동일하다.

## 감시 인디케이터 읽는 법

화면 하단에 감시 상태가 항상 떠 있다. 한 단계가 70ms라 깜빡임으로는 읽을 수
없으므로, **지속적으로 읽히는 정보**로 표시한다.

```
⠹ 감시 중 · 4초 전 갱신 · 명령 로그
```

| 보이는 것 | 의미 |
|---|---|
| 스피너가 돈다 (`⠋⠙⠹⠸…`) | 감시가 살아 움직이는 중 |
| `n초 전 갱신` | 데이터 신선도. 숫자가 계속 커지면 느려지는 중 |
| 끝의 이름 | 지금 수행 중인 감시 단계 |
| `⚠ 감시 오류: …` (빨강) | 고장. 조용히 넘어가지 않는다 |

감시는 **루프 한 바퀴에 단계 하나씩**만 수행한다. 한 번에 몰아서 하면 docker
호출 4개가 연달아 일어나 UI가 240ms 멈추고, 그동안 키 입력이 처리되지 않아
"키가 안 먹는다"처럼 느껴진다. 나눠 돌리면 프리즈가 70ms대로 줄어든다.

## 판정 구조

두 축으로 본다. 이 분리가 이 게임의 핵심이다.

| 축 | 무엇을 보는가 | 근거 |
|---|---|---|
| `state` 목표 | **결과** — 목표 상태에 도달했는가 | DB 상태 폴링(2초 주기) |
| `constraints` | **방법** — 어떻게 도달했는가 | `mysql.general_log` 명령 이력 |
| `quiz` 목표 | **이해** — 원인을 알고 고쳤는가 | `exam.py` 채점기 재사용 |

상태만 보면 "범인만 정확히 KILL"과 "전부 쓸어버리기"가 똑같은 정상 복구다.
실무에서는 전혀 다른 이야기이므로 방법도 채점한다.

`quiz`가 따로 있는 이유는 단순하다 — **"원인을 식별했다"는 DB 상태로 증명할 수 없다.**
아무 생각 없이 전부 재시작해도 상태는 정상이 된다.

### 명령 이력을 읽는 방식

`mysql.general_log`는 **CSV 엔진**이라 인덱스가 없어 조회할 때마다 전체 스캔이다.
그래서 엔진은 **읽으면서 곧바로 로그를 비운다**(`SELECT …; TRUNCATE TABLE
mysql.general_log`). 한 접속 안에서 순서가 맞아떨어진다:

1. `Connect` + 클라이언트 배너 질의 + `SET SESSION sql_log_off = 1` → 로그에 남음
2. `SELECT … WHERE user_host LIKE 'dba%'` → 로깅 안 됨, 플레이어 명령 반환
3. `TRUNCATE` → 로깅 안 됨, **1번이 남긴 자기 흔적까지 함께 삭제**

이렇게 하지 않으면 엔진이 **자기가 읽어야 할 로그를 자기가 오염시킨다** — 폴링
접속마다 3행씩 쌓여 10분이면 수천 행이 되고 스캔이 점점 느려진다. 비우면 테이블이
3행 안팎으로 고정되어 스캔 비용이 세션 길이와 무관해진다.

대신 매 조회가 "직전 조회 이후의 새 명령"만 돌려주므로, **엔진이 누적한다**
(`run_watch_step`의 `commands` 단계). 스테이지 판정은 누적된 전체 목록으로 한다.

### 사용자 분리

판정의 토대다. `shooting/lab/seed/03-users.sql` 참고.

| 계정 | 역할 | 판정에서의 의미 |
|---|---|---|
| `dba@%` | 플레이어 | 엔진은 `general_log`에서 이 사용자의 명령만 감시 |
| `app@%` | 엔진이 띄우는 범인/피해 세션 | 앱 트래픽처럼 보이되 플레이어 로그를 오염시키지 않음 |
| `root@localhost` | 엔진 자신 (docker exec 소켓) | `user_host`가 달라 자연히 걸러짐 |

`dba`에게 `SHUTDOWN` 권한은 일부러 주지 않는다 — SQL `RESTART`를 막고, "그냥 껐다
켜기" 반사는 `docker restart` 감지로 잡는다.

> **알려진 한계.** `dba`에게는 이후 튜닝 스테이지를 위해 `SYSTEM_VARIABLES_ADMIN`이
> 있고, 그 권한이면 엔진과 같은 방법(`SET SESSION sql_log_off = 1`)으로 자기 명령을
> 로그에서 숨길 수 있다. 이 게임은 학습 도구이지 부정 방지 시스템이 아니므로
> 막지 않는다. 등급을 속여서 얻는 게 없다는 점도 감안했다.

### `setup` — 장애 주입

**setup은 반드시 멱등이어야 한다.** 이전 판의 잔재를 지우고, 데이터를 되돌리고,
그 다음 장애를 주입한다. 그래야 스테이지를 순서 무관하게 다시 플레이할 수 있다.

엔진이 자동으로 해주는 것(스테이지가 선언할 필요 없음):
1. 남아있는 `app` 세션 정리
2. `mysql.general_log` 비우기 — 플레이어 명령 이력의 시작점을 0으로
3. **모든 `state` 목표가 미충족이 될 때까지 대기** — 장애가 실제로 걸린 것을 확인하고 출발한다

세 번째가 없으면, 피해 세션이 아직 잠금을 잡으러 가기 전의 짧은 창에서 타이머가
돌기 시작해 플레이어가 아무것도 안 했는데 클리어돼버린다.

| `type` | 동작 |
|---|---|
| `sql` | `on` 컨테이너에서 root로 실행. **데이터 복원은 여기서 한다** |
| `session` | 분리 세션 1개 기동 |
| `sessions` | 분리 세션 `count`개 기동 |

세션 단계의 필드: `on`(기본 `primary`), `user`/`password`(기본 `app`/`app`),
`name`(로그 표시용), `count`(`sessions`만), `culprit`.

**`culprit: true`가 결정적이다.** 이 단계로 뜬 세션의 pid를 엔진이 기억해두고,
나중에 "범인 외 세션을 KILL했는가"를 가려낸다. 표시하지 않으면 `kill_precision`
제약이 성립하지 않는다.

### `objectives` — 목표

공통: `id`(스테이지 안에서 유일), `type`, `label`(화면 표시).

**`type: "state"`** — DB 상태로 판정.

| 필드 | 설명 |
|---|---|
| `on` | `primary` 또는 `replica` |
| `query` | **단일 스칼라를 돌려주는** SQL. 첫 행 첫 컬럼만 본다 |
| `expect` | `{"op": ..., "value": ...}` |
| `hold_seconds` | 이 시간만큼 **연속으로** 유지돼야 인정 |

연산자: `eq` `ne` `lt` `lte` `gt` `gte` `contains` `in`.
`mysql -N -B` 출력은 전부 문자열이지만 엔진이 숫자로 바꿔 비교하므로
`{"op": "eq", "value": 0}`은 `"0"`과 맞는다.

`hold_seconds`를 생략하면 즉시 인정된다. **장애 대응 목표에는 반드시 넣어라** —
없으면 폴링 사이에 스쳐 지나간 순간적 정상 상태로 클리어된다.

**`type: "quiz"`** — 진단 판정. `question`은 `exam.py` 문항 스키마와 같다
(`docs/exam-authoring.md` 참고). `mcq`와 `short`를 지원한다.

`trigger: {"after_seconds": N}`을 주면 N초 뒤 자동으로 화면이 뜬다.
**생략하면 자동으로 뜨지 않고** 플레이어가 `r` 키로 직접 연다. 상황을 보기도 전에
문항이 튀어나오면 '상황 보고'가 아니라 그냥 퀴즈가 되므로, 자동 발동은
스테이지당 한 개 정도로 아껴 쓴다.

### `constraints` — 금지 행동

위반해도 스테이지는 실패하지 않는다. 등급만 내려간다(목숨 없음).

| `detect` | 판정 방법 |
|---|---|
| `container_restart` | 스테이지 시작 시각과 컨테이너 `StartedAt` 비교 |
| `kill_precision` | `general_log`의 `KILL` 대상이 `culprit` 세션인지. `max_extra_kills`(기본 0) 초과 시 위반 |

### 등급

클리어 기본이 C. 아래 넷 중 채운 개수만큼 올라간다 — 4개 S / 3개 A / 2개 B / 0~1개 C.

1. 소요 시간 ≤ `target_seconds`
2. 힌트 0회
3. 금지 행동 위반 0건
4. 진단 문항 전부 정답

**제한 시간은 하드 리밋이 아니다.** 초과해도 계속 플레이할 수 있고 등급만 내려간다.

## 새 스테이지를 추가할 때

1. `shooting/stages/<world>-<n>-<slug>.json` 작성
2. `./shoot doctor`로 정의 검증 (`validate_stage`가 형식 오류를 잡는다)
3. 실제로 한 판 플레이 — 특히 **아무것도 하지 않고 방치했을 때 클리어되지 않는지** 확인
4. 관련 챕터가 있으면 `README.md`에서 서로 연결

`tests/test_shooting.py`의 `ShippedStagesTest`가 저장소의 모든 스테이지 정의를
자동 검증하므로, 새 스테이지를 넣으면 테스트가 함께 지켜준다.

## 랩 구조

`shooting/lab/compose.yaml` — `dbshoot-primary`(3306), `dbshoot-replica`(3307).

두 서버는 **복제가 구성되지 않은 상태**로 뜬다. binlog/GTID만 켜져 있고
`CHANGE REPLICATION SOURCE`는 하지 않는다 — 복제 구성 자체가 구축 스테이지의
과제이기 때문이다. 장애 스테이지는 `setup`에서 필요한 배선을 직접 한다.

`log_output = TABLE` 설정 덕분에 명령 이력이 `mysql.general_log` **테이블**로
들어가고, 파일을 tail 하는 대신 SQL로 조회할 수 있다.

### 알아둘 함정

엔진이 `app` 세션을 띄울 때 `mysql --no-defaults`를 쓴다. MySQL 클라이언트의
옵션 우선순위는 **명령줄 > 옵션 파일 > 환경변수**라서, 컨테이너 안
`/root/.my.cnf`의 root 비밀번호가 `MYSQL_PWD`를 이겨버린다. `--no-defaults`가
없으면 `app` 계정 인증이 조용히 실패하고 장애가 주입되지 않는다.

## 다른 DBMS 추가

스테이지 JSON에 `dbms` 필드가 이미 있다. PostgreSQL·Oracle 버전을 넣을 때는
스테이지 파일을 벤더별로 나누고, `shooting/lab`에 해당 서비스를 추가한 뒤
`scripts/shooting.py`의 `CONTAINERS`와 `mysql()` 상당 함수를 벤더별로 분기한다.
`mysql.general_log`에 해당하는 감시 소스(PostgreSQL은 `log_statement = 'all'`)를
먼저 확인할 것 — 판정 구조 전체가 거기에 얹혀 있다.
