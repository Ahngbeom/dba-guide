# 장애 대응 게임 — 스테이지 작성 규약

`./shoot`는 실제 로컬 MySQL에 장애를 주입하고, 플레이어가 **자기 터미널의 진짜
mysql 클라이언트**로 대응하는 동안 DB 상태와 명령 이력을 감시해 클리어를 판정한다.

읽는 콘텐츠(챕터)와 확인하는 도구(`./exam`)에 이어, **손으로 겪는** 세 번째 축이다.

- 엔진: `scripts/shooting.py` (표준 라이브러리만)
- 랩: `shooting/lab/compose.yaml`
- 스테이지: `shooting/stages/*.json`
- 테스트: `python3 -m unittest discover -s tests`

## 실행

```bash
./shoot doctor          # 사전 점검 (docker / 포트 / 클라이언트 / 스테이지 정의)
./shoot up              # 랩 기동 (최초 1회는 이미지 내려받기로 몇 분)
./shoot --list          # 스테이지 목록
./shoot                 # 스테이지를 골라 플레이
./shoot 1-3-lock-contention
./shoot down            # 랩 정리 (볼륨 포함 — 확인 프롬프트가 뜬다)
```

```bash
./shoot notes           # 지난 정리 노트(포스트모템) 보기
```

DB에 접근하는 방법은 두 가지이고, 둘 다 언제든 쓸 수 있다.

- **플레이 화면에서 `c`** — 게임이 잠시 물러나고 진짜 mysql 클라이언트가 뜬다.
- **외부 터미널** — 접속 명령은 게임 화면 상단에 항상 떠 있다.

```bash
MYSQL_PWD=shoot mysql -h127.0.0.1 -P3306 -udba -Dshop
```

## mysql 접속 (`c`)

`c` 키를 누르면 게임이 잠시 물러나고 **진짜 `mysql` 클라이언트**가 이 터미널에
뜬다. `exit`(또는 `\q`)로 나가면 게임 화면으로 돌아와 즉시 갱신된다.

```
────────────────────────────────────────────────────────────
 1-3-lock-contention  락 지옥   04:12   [x][x][ ][ ]
   [ ] 대기 세션 해소
 게임 화면으로 돌아가려면  exit  (또는 \q)
────────────────────────────────────────────────────────────

[1-3-lock-contention] mysql> SELECT * FROM performance_schema.data_locks LIMIT 1;
*************************** 1. row ***************************
               ENGINE: INNODB
        OBJECT_SCHEMA: shop
```

### 왜 직접 만들지 않는가

한때 이 자리에 curses로 만든 SQL 콘솔이 있었다. 편집기·페이저·히스토리·자동완성을
손으로 재구현했고(363줄), 좁은 키맵에 편집기 + 페이저 + 게임 HUD를 욱여넣느라
키 배정이 계속 충돌했다. 결과는 모든 항목에서 원본보다 못했다.

| 항목 | 직접 만든 콘솔 | 진짜 클라이언트 |
|---|---|---|
| 편집 | 자체 구현 | readline 전체 + `~/.mysql_history` 영속 |
| 기록 | `↑↓`만 | `↑↓` + `Ctrl+R` 검색 |
| 자동완성 | 스키마·테이블 | 스키마·테이블·**컬럼** (`--auto-rehash`) |
| 넓은 결과 | 수동 가로 스크롤 | `--auto-vertical-output` 자동 세로 전환 |
| 긴 결과 | 2,000줄에서 잘라냄 | `--pager='less -SFX'` 스크롤·검색 |
| 세션 | 질의마다 끊김 | 지속 세션(트랜잭션·`SET SESSION` 가능) |

`scripts/shooting.py`의 `run_in_terminal()`이 그 통로다 —
`curses.def_prog_mode()` → `endwin()` → 외부 도구 → `reset_prog_mode()`.
편집기·페이저도 같은 통로를 쓴다. **터미널 도구를 curses 안에 다시 만들지 마라.**

### 넓은 결과가 잘리지 않는 이유

`SELECT * FROM performance_schema.data_locks`는 한 줄이 254칸이다.
`--auto-vertical-output`이 행이 터미널보다 넓으면 알아서 `\G` 세로 출력으로
바꾼다. 긴 결과는 `less`(있을 때만 `--pager`로 붙인다)로 스크롤·검색한다.

### 판정은 그대로다

클라이언트도 `dba` 계정으로 접속하므로 `general_log` 귀속이 외부 터미널과 같다.
판정이 보는 것은 "어디서 쳤는가"가 아니라 "로그에 누구로 기록됐는가"다.

**알려진 함정**: MySQL 옵션 우선순위는 명령줄 > 옵션 파일 > 환경변수라,
사용자의 `~/.my.cnf`에 `password=`가 있으면 `MYSQL_PWD`를 이겨 인증이 실패한다.
접속에 실패하면 게임이 이 가능성을 안내한다.

**감시는 멈춘다**: 클라이언트가 떠 있는 동안에는 폴링이 돌지 않는다. 거기서 장애를
고쳐도 빠져나온 뒤부터 `hold_seconds`가 세어진다.

## 정리 노트 (포스트모템)

스테이지가 끝나면 회고 작성을 권한다. 이건 부가 기능이 아니라 **학습 루프를 닫는
조각**이다 — [`03-advanced/09-incident-response-and-postmortem.md`](../03-advanced/09-incident-response-and-postmortem.md)가
가르치는 게 정확히 포스트모템이고, 장애 직후 그 템플릿으로 회고를 쓰는 것이 그
챕터의 실습이다.

### 초안은 사실만 채운다

엔진은 이미 재료를 갖고 있다 — 플레이어가 친 명령, 틀린 진단 문항, 금지 행동
위반, 소요 시간, 힌트 사용. 이걸로 초안을 만들고 `$VISUAL`/`$EDITOR`를 띄운다.

| 절 | 처리 |
|---|---|
| 요약(영향·등급) · 타임라인 · 잘된 점 · 아쉬운 점 | **채움** |
| 근본 원인 · 5 Whys · 재발 방지 · Blameless 노트 | **빈칸** |

분석을 미리 채워주면 회고 연습이 되지 않는다.

오답노트는 별도 문서로 분리하지 않고 "아쉬운 점" 절에 녹인다(문항·정답·해설).
회고 하나로 통합하는 편이 나중에 다시 볼 때 쓸모 있다.

### 해설은 편집기를 닫은 뒤에 붙는다

스테이지의 정답 해설(`debrief`)은 **초안에 없다.** 편집기를 닫으면 그때
`## 스테이지 해설 (공식)` 절로 파일 끝에 덧붙는다.

```
[쓸 때]                          [파일에 남는 최종본]
## 근본 원인 분석 (5 Whys)        ## 근본 원인 분석 (5 Whys)
1. 왜? →                         1. 왜? → 내가 쓴 답
   (해설 없음)                    ---
                                 ## 스테이지 해설 (공식)
                                 범인은 커밋하지 않은 트랜잭션…
                                 ## 대조 메모
```

이 순서가 둘을 모두 지킨다 — **쓸 때는 안 보이고**(그래야 5 Whys를 스스로 쓴다),
**나중에 `n` 키로 꺼내 볼 때는 내 분석과 공식 해설이 한 문서에** 나란히 있다.
실제 포스트모템 리뷰(초안 → 사실 확인 → 개정)와 같은 흐름이다.

덧붙인 뒤 `대조 메모를 남기시겠습니까? [y/N]`을 묻는다. 건너뛰어도 빈
`## 대조 메모` 절이 문서에 남아 나중에 직접 채울 수 있다.
`append_debrief()`는 멱등이라 노트를 다시 편집해도 해설이 중복되지 않는다.

> **포기한 판에는 해설을 붙이지 않는다.** 붙이면 '포기'가 정답을 얻는 지름길이
> 된다. 스테이지는 다시 플레이할 수 있으므로 클리어했을 때만 해설을 준다.
> (포기해도 회고는 쓸 수 있다 — 오히려 그때가 더 필요하다.)

### 저장과 열람

```
.shooting-progress/notes/<스테이지 id>/<YYYYMMDD-HHMMSS>-<등급>.md
```

`.shooting-progress/`는 `.gitignore`에 있다(개인 학습 기록).

- 플레이 중 `n` 키 — 지난 노트를 **현재 스테이지 먼저, 최신순**으로 이어 붙여
  페이저로 넘긴다. 감점 없다. 새벽 3시에 자기가 쓴 Runbook을 보는 건 실무 그 자체고,
  다음에 볼 것을 지금 쓰게 만드는 동기가 된다.
- 게임 밖에서는 `./shoot notes [<스테이지 id>]`

뷰어를 만들지 않는다 — `less`가 스크롤·검색(`/`)을 이미 다 한다. 목록 UI조차
필요 없다: 이어 붙여 넘기면 끝이다.

## 조작키

| 화면 | 키 | 동작 |
|---|---|---|
| 플레이 | `c` | **진짜 mysql 클라이언트 열기** (`exit`으로 복귀) |
| 플레이 | `n` | **지난 정리 노트 보기** (페이저, 감점 없음) |
| 플레이 | `r` | 상황 보고(진단 문항) 열기 |
| 플레이 | `h` | 힌트 (1회라도 쓰면 힌트 보너스 상실) |
| 플레이 | `q` | 스테이지 포기 |
| 객관식 문항 | `↑` `↓` 또는 `k` `j` | 선택 이동 |
| 객관식 문항 | 숫자 `1`~`9` | 바로 선택 |
| 객관식 문항 | `Enter` | 제출 |
| 객관식 문항 | `Esc` / `b` / `q` | **제출하지 않고 닫기** (고르던 위치 보존) |
| 주관식 문항 | `Enter` | 제출 |
| 주관식 문항 | `Esc` | **제출하지 않고 닫기** (입력 내용 보존) |

mysql 클라이언트 안에서는 그 클라이언트의 키가 그대로 동작한다(readline, `Ctrl+R`
기록 검색, `Tab` 완성). 페이저 안에서는 `less`의 키(`/` 검색 등)를 쓴다.

문항의 `Esc`는 `exam.py`의 `Esc 닫기(임시저장)` 규약과 같다. 닫아도 목표는 `[?]`로 남고 `r`로
다시 열면 이어서 답할 수 있다. 주관식에서 `b`/`q`를 나가는 키로 쓸 수 없는 이유는
모든 인쇄 가능 문자가 입력값이기 때문이다.

터미널이 실제로 어떤 값을 보내는지 확인해야 하면 `./exam --keydebug`를 쓴다.
두 러너가 같은 `scripts/tui.py` 키 코드를 공유하므로 결과가 동일하다.

## 감시 인디케이터 읽는 법

화면 하단에 감시 상태가 항상 떠 있다. 한 단계가 70ms라 깜빡임으로는 읽을 수
없으므로, **지속적으로 읽히는 정보**로 표시한다.

```
⠹ 감시 중 · 4초 전 갱신 · 명령 로그
```

| 보이는 것 | 의미 |
|---|---|
| 스피너가 돈다 (`⠋⠙⠹⠸…`) | 감시가 살아 움직이는 중 |
| `n초 전 갱신` | 데이터 신선도. 숫자가 계속 커지면 느려지는 중 |
| 끝의 이름 | 지금 수행 중인 감시 단계 |
| `⚠ 감시 오류: …` (빨강) | 고장. 조용히 넘어가지 않는다 |

감시는 **루프 한 바퀴에 단계 하나씩**만 수행한다. 한 번에 몰아서 하면 docker
호출 4개가 연달아 일어나 UI가 240ms 멈추고, 그동안 키 입력이 처리되지 않아
"키가 안 먹는다"처럼 느껴진다. 나눠 돌리면 프리즈가 70ms대로 줄어든다.

## 판정 구조

두 축으로 본다. 이 분리가 이 게임의 핵심이다.

| 축 | 무엇을 보는가 | 근거 |
|---|---|---|
| `state` 목표 | **결과** — 목표 상태에 도달했는가 | DB 상태 폴링(2초 주기) |
| `constraints` | **방법** — 어떻게 도달했는가 | `mysql.general_log` 명령 이력 |
| `quiz` 목표 | **이해** — 원인을 알고 고쳤는가 | `exam.py` 채점기 재사용 |

상태만 보면 "범인만 정확히 KILL"과 "전부 쓸어버리기"가 똑같은 정상 복구다.
실무에서는 전혀 다른 이야기이므로 방법도 채점한다.

`quiz`가 따로 있는 이유는 단순하다 — **"원인을 식별했다"는 DB 상태로 증명할 수 없다.**
아무 생각 없이 전부 재시작해도 상태는 정상이 된다.

### 명령 이력을 읽는 방식

`mysql.general_log`는 **CSV 엔진**이라 인덱스가 없어 조회할 때마다 전체 스캔이다.
그래서 엔진은 **읽으면서 곧바로 로그를 비운다**(`SELECT …; TRUNCATE TABLE
mysql.general_log`). 한 접속 안에서 순서가 맞아떨어진다:

1. `Connect` + 클라이언트 배너 질의 + `SET SESSION sql_log_off = 1` → 로그에 남음
2. `SELECT … WHERE user_host LIKE 'dba%'` → 로깅 안 됨, 플레이어 명령 반환
3. `TRUNCATE` → 로깅 안 됨, **1번이 남긴 자기 흔적까지 함께 삭제**

이렇게 하지 않으면 엔진이 **자기가 읽어야 할 로그를 자기가 오염시킨다** — 폴링
접속마다 3행씩 쌓여 10분이면 수천 행이 되고 스캔이 점점 느려진다. 비우면 테이블이
3행 안팎으로 고정되어 스캔 비용이 세션 길이와 무관해진다.

대신 매 조회가 "직전 조회 이후의 새 명령"만 돌려주므로, **엔진이 누적한다**
(`run_watch_step`의 `commands` 단계). 스테이지 판정은 누적된 전체 목록으로 한다.

### 사용자 분리

판정의 토대다. `shooting/lab/seed/03-users.sql` 참고.

| 계정 | 역할 | 판정에서의 의미 |
|---|---|---|
| `dba@%` | 플레이어 | 엔진은 `general_log`에서 이 사용자의 명령만 감시 |
| `app@%` | 엔진이 띄우는 범인/피해 세션 | 앱 트래픽처럼 보이되 플레이어 로그를 오염시키지 않음 |
| `repl@%` | replica가 binlog를 받아갈 때 쓰는 계정 | 사람의 명령이 아니라 판정에 잡히지 않음 |
| `root@localhost` | 엔진 자신 (docker exec 소켓) | `user_host`가 달라 자연히 걸러짐 |

`dba`에게 `SHUTDOWN` 권한은 일부러 주지 않는다 — SQL `RESTART`를 막고, "그냥 껐다
켜기" 반사는 `docker restart` 감지로 잡는다.

**명령 로그는 서버마다 따로 있다.** 엔진은 감시 대상 컨테이너를 모두 읽고,
`KILL` 대상과 범인 pid를 `(서버, pid)` 쌍으로 다룬다. pid는 서버마다 따로
매겨지므로, 서버를 함께 보지 않으면 replica의 범인 12번을 근거로 primary의
무고한 12번을 죽인 것이 무사통과한다. 감시 대상은 `setup`과 `objectives`의
`on` 값에서 모은다 — 장애를 넣은 서버와 플레이어가 손대야 할 서버가 다를 수 있다.

> **알려진 한계.** `dba`에게는 이후 튜닝 스테이지를 위해 `SYSTEM_VARIABLES_ADMIN`이
> 있고, 그 권한이면 엔진과 같은 방법(`SET SESSION sql_log_off = 1`)으로 자기 명령을
> 로그에서 숨길 수 있다. 이 게임은 학습 도구이지 부정 방지 시스템이 아니므로
> 막지 않는다. 등급을 속여서 얻는 게 없다는 점도 감안했다.

## 스테이지 JSON 스키마

`shooting/stages/1-3-lock-contention.json`이 참고 구현이다.

### 최상위

| 필드 | 필수 | 설명 |
|---|---|---|
| `id` | ✅ | 파일명(확장자 제외)과 맞춘다. `<월드>-<스테이지>-<슬러그>` |
| `title` | ✅ | 스테이지 이름 |
| `objectives` | ✅ | 목표 목록(아래) |
| `world`, `stage` | | 진행 구조상의 위치 |
| `kind` | | `incident`(장애 대응) 또는 `build`(구축). 목록에서 🔥/🔧로 표시 |
| `dbms` | | 현재는 `mysql`. 벤더별 스테이지를 나눌 때 쓴다 |
| `brief` | | 플레이어에게 보여줄 상황 설명. **증상만 쓰고 원인은 쓰지 않는다** |
| `target_seconds` | | 시간 보너스 기준. 하드 리밋이 아니다 |
| `connect_hint` | | 화면 상단에 띄울 접속 명령 |
| `setup` | | 장애 주입 단계(아래) |
| `constraints` | | 금지 행동(아래) |
| `hints` | | 순서대로 소비된다. 1회라도 쓰면 힌트 보너스를 잃는다 |
| `debrief` | | 클리어 후 후일담. 진짜 원인과 재발 방지책을 여기서 가르친다 |

### `setup` — 장애 주입

**setup은 반드시 멱등이어야 한다.** 이전 판의 잔재를 지우고, 데이터를 되돌리고,
그 다음 장애를 주입한다. 그래야 스테이지를 순서 무관하게 다시 플레이할 수 있다.

엔진이 자동으로 해주는 것(스테이지가 선언할 필요 없음):
1. 남아있는 `app` 세션 정리
2. `mysql.general_log` 비우기 — 플레이어 명령 이력의 시작점을 0으로
3. **모든 `state` 목표가 미충족이 될 때까지 대기** — 장애가 실제로 걸린 것을 확인하고 출발한다

세 번째가 없으면, 피해 세션이 아직 잠금을 잡으러 가기 전의 짧은 창에서 타이머가
돌기 시작해 플레이어가 아무것도 안 했는데 클리어돼버린다.

| `type` | 동작 |
|---|---|
| `sql` | `on` 컨테이너에서 root로 실행. **데이터 복원은 여기서 한다** |
| `session` | 분리 세션 1개 기동 |
| `sessions` | 분리 세션 `count`개 기동 |
| `wait_gtid_sync` | `on`이 `source`를 따라잡을 때까지 대기(아래) |

세션 단계의 필드: `on`(기본 `primary`), `user`/`password`(기본 `app`/`app`),
`name`(로그 표시용), `count`(`sessions`만), `culprit`.

`wait_gtid_sync`의 필드: `on`(따라잡아야 하는 쪽), `source`(기본 `primary`),
`timeout_seconds`(기본 60). 이 단계만 `sql`이 없다 — 대기 자체가 내용이다.
엔진이 자동으로 해주는 3번(모든 `state` 목표가 미충족이 될 때까지 대기)과 다르다.
그 대기는 **장애가 걸렸는지**를 보지만, 이건 장애를 걸기 **전에** 끝나 있어야 하는
초기 동기화다. 없으면 "초기 20만 행이 아직 흐르는 중"과 "장애로 밀렸다"가 섞여
플레이어가 자기가 만들지 않은 지연을 진단하게 된다. 따라잡지 못하면 조용히
넘어가지 않고 setup을 실패시킨다.

### 멱등성을 지키는 관용구

**있을 때만 지우기.** `DROP INDEX`/`DROP COLUMN`은 대상이 없으면 에러라
`IF EXISTS`가 없는 자리에서는 가드가 필요하다. 플레이어가 붙인 이름을 미리 알 수
없으므로 **이름이 아니라 조건으로** 찾아 지우는 편이 안전하다.

```sql
SET @drops := (SELECT GROUP_CONCAT(CONCAT('DROP INDEX `', index_name, '`') SEPARATOR ', ')
  FROM (SELECT DISTINCT index_name FROM information_schema.statistics
        WHERE table_schema='shop' AND table_name='orders'
          AND index_name NOT IN ('PRIMARY','idx_status','idx_customer')) i);
SET @s := IF(@drops IS NULL, 'DO 0', CONCAT('ALTER TABLE shop.orders ', @drops));
PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
```

**바뀌지 않는 UPDATE는 복제되지 않는다.** ROW 포맷에서는 값이 실제로 달라져야
행 이벤트가 생긴다. `SET status='PICKED'`가 이미 `'PICKED'`인 행에 걸리면 아무
이벤트도 남지 않아, 그 이벤트에 기대던 장애가 두 번째 판부터 걸리지 않는다.
복제 스테이지에서 특정 행의 변경을 장애의 방아쇠로 쓴다면 **먼저 다른 값으로
되돌려 두어라**(2-2가 `id=42`를 `'NEW'`로 되돌리는 이유).

**`culprit: true`가 결정적이다.** 이 단계로 뜬 세션의 pid를 엔진이 기억해두고,
나중에 "범인 외 세션을 KILL했는가"를 가려낸다. 표시하지 않으면 `kill_precision`
제약이 성립하지 않는다.

### `objectives` — 목표

공통: `id`(스테이지 안에서 유일), `type`, `label`(화면 표시).

**`type: "state"`** — DB 상태로 판정.

| 필드 | 설명 |
|---|---|
| `on` | `primary` 또는 `replica` |
| `query` | **단일 스칼라를 돌려주는** SQL. 첫 행 첫 컬럼만 본다 |
| `expect` | `{"op": ..., "value": ...}` |
| `hold_seconds` | 이 시간만큼 **연속으로** 유지돼야 인정 |
| `tolerate_error` | 조회 실패를 '고장'이 아니라 '미충족'으로 읽는다 |

`tolerate_error`는 **조회 대상이 아직 존재하지 않는 것이 정상인 목표**에만 쓴다.
복제를 붙이기 전의 빈 replica에서 `shop.orders`를 세면 당연히 에러인데, 감시는
오류를 삼키지 않는 것이 원칙이라 빨간 `⚠ 감시 오류`가 뜬다. 고장이 아니라 아직
도달하지 않은 상태이므로 오인이다. 기본값은 꺼져 있고, 켜지 않은 목표의 조회
실패는 지금처럼 그대로 드러난다 — 진짜 고장을 숨기지 않기 위해서다.

연산자: `eq` `ne` `lt` `lte` `gt` `gte` `contains` `in`.
`mysql -N -B` 출력은 전부 문자열이지만 엔진이 숫자로 바꿔 비교하므로
`{"op": "eq", "value": 0}`은 `"0"`과 맞는다.

`hold_seconds`를 생략하면 즉시 인정된다. **장애 대응 목표에는 반드시 넣어라** —
없으면 폴링 사이에 스쳐 지나간 순간적 정상 상태로 클리어된다.

**`type: "quiz"`** — 진단 판정. `question`은 `exam.py` 문항 스키마와 같다
(`docs/exam-authoring.md` 참고). `mcq`와 `short`를 지원한다.

`trigger: {"after_seconds": N}`을 주면 N초 뒤 자동으로 화면이 뜬다.
**생략하면 자동으로 뜨지 않고** 플레이어가 `r` 키로 직접 연다. 상황을 보기도 전에
문항이 튀어나오면 '상황 보고'가 아니라 그냥 퀴즈가 되므로, 자동 발동은
스테이지당 한 개 정도로 아껴 쓴다.

### `constraints` — 금지 행동

위반해도 스테이지는 실패하지 않는다. 등급만 내려간다(목숨 없음).

| `detect` | 판정 방법 |
|---|---|
| `container_restart` | 스테이지 시작 시각과 컨테이너 `StartedAt` 비교 |
| `kill_precision` | `general_log`의 `KILL` 대상이 `culprit` 세션인지. `max_extra_kills`(기본 0) 초과 시 위반 |

### 등급

클리어 기본이 C. 아래 넷 중 채운 개수만큼 올라간다 — 4개 S / 3개 A / 2개 B / 0~1개 C.

1. 소요 시간 ≤ `target_seconds`
2. 힌트 0회
3. 금지 행동 위반 0건
4. 진단 문항 전부 정답

**제한 시간은 하드 리밋이 아니다.** 초과해도 계속 플레이할 수 있고 등급만 내려간다.

## 랩 구조

`shooting/lab/compose.yaml` — `dbshoot-primary`(3306), `dbshoot-replica`(3307).

두 서버는 **복제가 구성되지 않은 상태**로 뜬다. binlog/GTID만 켜져 있고
`CHANGE REPLICATION SOURCE`는 하지 않는다 — 복제 구성 자체가 구축 스테이지의
과제이기 때문이다. 장애 스테이지는 `setup`에서 필요한 배선을 직접 한다.

`log_output = TABLE` 설정 덕분에 명령 이력이 `mysql.general_log` **테이블**로
들어가고, 파일을 tail 하는 대신 SQL로 조회할 수 있다.

### 알아둘 함정

엔진이 `app` 세션을 띄울 때 `mysql --no-defaults`를 쓴다. MySQL 클라이언트의
옵션 우선순위는 **명령줄 > 옵션 파일 > 환경변수**라서, 컨테이너 안
`/root/.my.cnf`의 root 비밀번호가 `MYSQL_PWD`를 이겨버린다. `--no-defaults`가
없으면 `app` 계정 인증이 조용히 실패하고 장애가 주입되지 않는다.

**`DEFINER` 프로시저는 `app` 세션을 숨긴다.** 스토어드 프로시저는 기본이
`SQL SECURITY DEFINER`인데, 그 안을 실행하는 동안 `information_schema.processlist`의
`user`가 **정의자(root)** 로 보고된다. 엔진은 `user='app'`으로 세션을 추적하므로,
부하 생성용 프로시저를 그냥 만들면 세션이 잡히지 않아 기동 대기가 20초를 헛돌고
판이 끝나도 정리되지 않아 다음 판까지 살아남는다. 부하 프로시저는 반드시
**`SQL SECURITY INVOKER`** 로 만든다.

**`DELIMITER`는 줄 단위 명령이다.** `sql` 단계는 `mysql -e`로 실행되는데,
`DELIMITER`는 클라이언트가 줄 단위로 해석한다. 프로시저를 만들 때 한 줄로 붙이면
`;`에서 잘려 문법 오류가 난다. JSON 문자열 안에 `\n`을 넣어 `DELIMITER //`와
`DELIMITER ;`가 각각 자기 줄을 갖게 해야 한다.

**엔진의 장부질은 binlog에 남기지 않는다.** 명령 로그를 비우는
`TRUNCATE TABLE mysql.general_log`는 그냥 두면 binlog에 실려 **replica에서도
실행된다.** 감시는 primary 로그를 먼저 읽고(=비우고) replica를 나중에 읽으므로,
그 사이 복제가 전달한 TRUNCATE가 replica의 로그를 지워 플레이어가 거기서 친
명령이 매 주기 증발한다. 그래서 `NO_BINLOG`(`SET SESSION sql_log_bin = 0`)를
앞에 붙인다. 반대로 **스테이지의 `sql` 단계는 복제되어야 한다** — 2-2의 센티널
행이 replica에 도달하는 것이 판정의 근거이기 때문이다.

## 다른 DBMS 추가

스테이지 JSON에 `dbms` 필드가 이미 있다. PostgreSQL·Oracle 버전을 넣을 때는
스테이지 파일을 벤더별로 나누고, `shooting/lab`에 해당 서비스를 추가한 뒤
`scripts/shooting.py`의 `CONTAINERS`와 `mysql()` 상당 함수를 벤더별로 분기한다.
`mysql.general_log`에 해당하는 감시 소스(PostgreSQL은 `log_statement = 'all'`)를
먼저 확인할 것 — 판정 구조 전체가 거기에 얹혀 있다.
