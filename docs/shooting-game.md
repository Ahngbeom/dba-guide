# 장애 대응 게임 — 스테이지 작성 규약

`./shoot`는 실제 로컬 MySQL에 장애를 주입하고, 플레이어가 **자기 터미널의 진짜
mysql 클라이언트**로 대응하는 동안 DB 상태와 명령 이력을 감시해 클리어를 판정한다.

읽는 콘텐츠(챕터)와 확인하는 도구(`./exam`)에 이어, **손으로 겪는** 세 번째 축이다.

- 엔진: `scripts/shooting.py` (표준 라이브러리만)
- 랩: `shooting/lab/compose.yaml`
- 스테이지: `shooting/stages/*.json`
- 테스트: `python3 -m unittest discover -s tests`

## 실행

```bash
./shoot doctor          # 사전 점검 (docker / 포트 / 클라이언트 / 스테이지 정의)
./shoot up              # 랩 기동 (최초 1회는 이미지 내려받기로 몇 분)
./shoot --list          # 스테이지 목록
./shoot                 # 스테이지를 골라 플레이
./shoot --dbms postgresql   # 그 DBMS 스테이지만 (선택 화면을 건너뛴다)
./shoot 1-3-lock-contention
./shoot down            # 랩 정리 (볼륨 포함 — 확인 프롬프트가 뜬다)
```

```bash
./shoot notes           # 지난 정리 노트(포스트모템) 보기
./shoot replay          # 마지막에 플레이한 판을 같은 시드로 다시
./shoot replay 1-2-deadlock   # 그 스테이지의 마지막 판으로
```

선택 화면은 **DBMS → 월드 → 스테이지**로 내려간다(`exam`이 DBMS → 티어 → 챕터로
가는 것과 같다). **DBMS가 하나뿐이면 그 단계는 나오지 않는다** — 선택지가 하나인
화면은 고를 것이 없는데 Enter만 요구하는 잡음이다. `--dbms`를 주면 그 단계를
건너뛴다.

인자 없이 `./shoot`을 실행하면 선택 화면이 뜬다. 클리어한 스테이지에는 **지난 최고
등급**이 붙는다 — S랭크 재도전이 이 게임을 다시 켜게 만드는 이유이므로 목록에서
바로 보이는 편이 낫다.

```
 스테이지를 고르세요
 ▶ 1) 🔥 1-3-lock-contention      락 지옥  [S]
   2) 🔥 1-4-metadata-lock        멈춘 배포
   3) 🔧 2-1-replication-setup    리포팅 서버 붙이기
   ↑↓ 또는 숫자 선택   Enter 시작   Esc/q 종료
```

선택은 **월드 → 스테이지 두 단계**다. `Esc`로 월드 선택으로 되돌아간다.
`exam`이 DBMS → 티어 → 챕터로 내려가는 것과 같은 방식이고, 단계마다
`tui.pick()`을 다시 부르는 것뿐이라 공용 선택기는 손대지 않는다.

```
 어느 월드부터 할까요
 ▶ 1) 월드 1 · 잠금과 대기        2개  [S]
   2) 월드 2 · 복제              2개
   3) 월드 3 · 자원 고갈          3개  [S]
   4) 월드 4 · 성능과 실행 계획     1개
```

월드 이름은 `scripts/shooting.py`의 `WORLD_TITLES`에 있다. **새 월드를 만들면
여기에 이름을 추가하라** — 없으면 '미분류'로 뜬다(테스트가 저장소의 모든 스테이지에
대해 이름이 있는지 확인한다). 월드 옆의 등급은 그 월드에서 받은 **가장 높은** 것이다.

정의가 깨진 스테이지도 목록에서 빼지 않고 `[오류]`로 보여준다 — 빼면 "파일은 있는데
목록에 없다"가 되어 더 헷갈린다. tty가 아니면 **한 단계 평문 목록**으로 낸다
(월드를 접두어로 붙인다 — 번호를 두 번 묻는 것이 더 번거롭다).

DB에 접근하는 방법은 두 가지이고, 둘 다 언제든 쓸 수 있다.

- **플레이 화면에서 `c`** — 게임이 잠시 물러나고 진짜 mysql 클라이언트가 뜬다.
- **외부 터미널** — 접속 명령은 게임 화면 상단에 항상 떠 있다.

```bash
MYSQL_PWD=shoot mysql -h127.0.0.1 -P3306 -udba -Dshop
```

## mysql 접속 (`c`)

`c` 키를 누르면 게임이 잠시 물러나고 **진짜 `mysql` 클라이언트**가 이 터미널에
뜬다. `exit`(또는 `\q`)로 나가면 게임 화면으로 돌아와 즉시 갱신된다.

```
────────────────────────────────────────────────────────────
 1-3-lock-contention  락 지옥   04:12   [x][x][ ][ ]
   [ ] 대기 세션 해소
 게임 화면으로 돌아가려면  exit  (또는 \q)
────────────────────────────────────────────────────────────

[1-3-lock-contention] mysql> SELECT * FROM performance_schema.data_locks LIMIT 1;
*************************** 1. row ***************************
               ENGINE: INNODB
        OBJECT_SCHEMA: shop
```

### 왜 직접 만들지 않는가

한때 이 자리에 curses로 만든 SQL 콘솔이 있었다. 편집기·페이저·히스토리·자동완성을
손으로 재구현했고(363줄), 좁은 키맵에 편집기 + 페이저 + 게임 HUD를 욱여넣느라
키 배정이 계속 충돌했다. 결과는 모든 항목에서 원본보다 못했다.

| 항목 | 직접 만든 콘솔 | 진짜 클라이언트 |
|---|---|---|
| 편집 | 자체 구현 | readline 전체 + `~/.mysql_history` 영속 |
| 기록 | `↑↓`만 | `↑↓` + `Ctrl+R` 검색 |
| 자동완성 | 스키마·테이블 | 스키마·테이블·**컬럼** (`--auto-rehash`) |
| 넓은 결과 | 수동 가로 스크롤 | `--auto-vertical-output` 자동 세로 전환 |
| 긴 결과 | 2,000줄에서 잘라냄 | `--pager='less -SFX'` 스크롤·검색 |
| 세션 | 질의마다 끊김 | 지속 세션(트랜잭션·`SET SESSION` 가능) |

`scripts/shooting.py`의 `run_in_terminal()`이 그 통로다 —
`curses.def_prog_mode()` → `endwin()` → 외부 도구 → `reset_prog_mode()`.
편집기·페이저도 같은 통로를 쓴다. **터미널 도구를 curses 안에 다시 만들지 마라.**

### 넓은 결과가 잘리지 않는 이유

`SELECT * FROM performance_schema.data_locks`는 한 줄이 254칸이다.
`--auto-vertical-output`이 행이 터미널보다 넓으면 알아서 `\G` 세로 출력으로
바꾼다. 긴 결과는 `less`(있을 때만 `--pager`로 붙인다)로 스크롤·검색한다.

### 서버가 둘 이상인 스테이지

복제 스테이지처럼 스테이지가 여러 서버를 건드리면 `c`가 먼저 **어디로 붙을지**
묻는다. 범인이 replica에 있는데 primary로만 갈 수 있으면 게임 안에서 현장에
도달할 수 없기 때문이다(2-2가 그렇다).

```
 어느 서버에 접속할까요
 ▶ 1) primary  (127.0.0.1:3306)
   2) replica  (127.0.0.1:3307)
```

선택지가 하나뿐인 스테이지에서는 이 화면을 띄우지 않고 바로 붙는다 — 물어볼
이유가 없다. 대상은 프롬프트에도 남는다: `[2-2-replication-lag@replica] mysql>`.
서버가 하나면 접두어가 잡음이므로 붙이지 않는다.

목록은 `client_targets()`가 `setup`·`objectives`의 `on` 값에서 모으므로(감시
대상과 같은 출처), 스테이지가 실제로 쓰는 서버만 나온다. 포트는
`PLAYER_PORTS`가 단일 출처이고 `compose.yaml`과 어긋나지 않는지 테스트가 대조한다.

### 판정은 그대로다

클라이언트도 `dba` 계정으로 접속하므로 `general_log` 귀속이 외부 터미널과 같다.
판정이 보는 것은 "어디서 쳤는가"가 아니라 "로그에 누구로 기록됐는가"다.
**어느 서버로 붙어도 마찬가지다** — 명령 로그는 이미 서버마다 따로 읽고,
`KILL` 대상도 `(서버, pid)` 쌍으로 귀속한다.

**알려진 함정**: MySQL 옵션 우선순위는 명령줄 > 옵션 파일 > 환경변수라,
사용자의 `~/.my.cnf`에 `password=`가 있으면 `MYSQL_PWD`를 이겨 인증이 실패한다.
접속에 실패하면 게임이 이 가능성을 안내한다.

**감시는 멈춘다**: 클라이언트가 떠 있는 동안에는 폴링이 돌지 않는다. 거기서 장애를
고쳐도 빠져나온 뒤부터 `hold_seconds`가 세어진다.

## 정리 노트 (포스트모템)

스테이지가 끝나면 회고 작성을 권한다. 이건 부가 기능이 아니라 **학습 루프를 닫는
조각**이다 — [`03-advanced/09-incident-response-and-postmortem.md`](../03-advanced/09-incident-response-and-postmortem.md)가
가르치는 게 정확히 포스트모템이고, 장애 직후 그 템플릿으로 회고를 쓰는 것이 그
챕터의 실습이다.

### 초안은 사실만 채운다

엔진은 이미 재료를 갖고 있다 — 플레이어가 친 명령, 틀린 진단 문항, 금지 행동
위반, 소요 시간, 힌트 사용. 이걸로 초안을 만들고 `$VISUAL`/`$EDITOR`를 띄운다.

| 절 | 처리 |
|---|---|
| 요약(영향·등급) · 타임라인 · 잘된 점 · 아쉬운 점 | **채움** |
| 근본 원인 · 5 Whys · 재발 방지 · Blameless 노트 | **빈칸** |

분석을 미리 채워주면 회고 연습이 되지 않는다.

오답노트는 별도 문서로 분리하지 않고 "아쉬운 점" 절에 녹인다(문항·정답·해설).
회고 하나로 통합하는 편이 나중에 다시 볼 때 쓸모 있다.

### 해설은 편집기를 닫은 뒤에 붙는다

스테이지의 정답 해설(`debrief`)은 **초안에 없다.** 편집기를 닫으면 그때
`## 스테이지 해설 (공식)` 절로 파일 끝에 덧붙는다.

```
[쓸 때]                          [파일에 남는 최종본]
## 근본 원인 분석 (5 Whys)        ## 근본 원인 분석 (5 Whys)
1. 왜? →                         1. 왜? → 내가 쓴 답
   (해설 없음)                    ---
                                 ## 스테이지 해설 (공식)
                                 범인은 커밋하지 않은 트랜잭션…
                                 ## 대조 메모
```

이 순서가 둘을 모두 지킨다 — **쓸 때는 안 보이고**(그래야 5 Whys를 스스로 쓴다),
**나중에 `n` 키로 꺼내 볼 때는 내 분석과 공식 해설이 한 문서에** 나란히 있다.
실제 포스트모템 리뷰(초안 → 사실 확인 → 개정)와 같은 흐름이다.

덧붙인 뒤 `대조 메모를 남기시겠습니까? [y/N]`을 묻는다. 건너뛰어도 빈
`## 대조 메모` 절이 문서에 남아 나중에 직접 채울 수 있다.
`append_debrief()`는 멱등이라 노트를 다시 편집해도 해설이 중복되지 않는다.

> **포기한 판에는 해설을 붙이지 않는다.** 붙이면 '포기'가 정답을 얻는 지름길이
> 된다. 스테이지는 다시 플레이할 수 있으므로 클리어했을 때만 해설을 준다.
> (포기해도 회고는 쓸 수 있다 — 오히려 그때가 더 필요하다.)

### 저장과 열람

```
.shooting-progress/notes/<스테이지 id>/<YYYYMMDD-HHMMSS>-<등급>.md
```

`.shooting-progress/`는 `.gitignore`에 있다(개인 학습 기록).

- 플레이 중 `n` 키 — 지난 노트를 **현재 스테이지 먼저, 최신순**으로 이어 붙여
  페이저로 넘긴다. 감점 없다. 새벽 3시에 자기가 쓴 Runbook을 보는 건 실무 그 자체고,
  다음에 볼 것을 지금 쓰게 만드는 동기가 된다.
- 게임 밖에서는 `./shoot notes [<스테이지 id>]`

뷰어를 만들지 않는다 — `less`가 스크롤·검색(`/`)을 이미 다 한다. 목록 UI조차
필요 없다: 이어 붙여 넘기면 끝이다.

## 조작키

| 화면 | 키 | 동작 |
|---|---|---|
| 플레이 | `c` | **진짜 mysql 클라이언트 열기** (`exit`으로 복귀). 서버가 둘 이상이면 대상을 먼저 고른다 |
| 서버 선택 | `↑` `↓` / `k` `j` / 숫자 | 선택·이동, `Enter` 접속, `Esc`/`q` 취소 |
| 플레이 | `n` | **지난 정리 노트 보기** (페이저, 감점 없음) |
| 플레이 | `r` | 상황 보고(진단 문항) 열기 |
| 플레이 | `h` | 힌트 (1회라도 쓰면 힌트 보너스 상실) |
| 플레이 | `q` | 스테이지 포기 (확인 화면에서 `y`를 눌러야 진행) |
| 객관식 문항 | `↑` `↓` 또는 `k` `j` | 선택 이동 |
| 객관식 문항 | 숫자 `1`~`9` | 바로 선택 |
| 객관식 문항 | `Enter` | 제출 |
| 객관식 문항 | `Esc` / `b` / `q` | **제출하지 않고 닫기** (고르던 위치 보존) |
| 주관식 문항 | `Enter` | 제출 |
| 주관식 문항 | `Esc` | **제출하지 않고 닫기** (입력 내용 보존) |

mysql 클라이언트 안에서는 그 클라이언트의 키가 그대로 동작한다(readline, `Ctrl+R`
기록 검색, `Tab` 완성). 페이저 안에서는 `less`의 키(`/` 검색 등)를 쓴다.

문항의 `Esc`는 `exam.py`의 `Esc 닫기(임시저장)` 규약과 같다. 닫아도 목표는 `[?]`로 남고 `r`로
다시 열면 이어서 답할 수 있다. 주관식에서 `b`/`q`를 나가는 키로 쓸 수 없는 이유는
모든 인쇄 가능 문자가 입력값이기 때문이다.

객관식 문항에서 `q`가 '닫기'인 탓에, 같은 손버릇이 플레이 화면에서는 판을 통째로
날릴 수 있다. 그래서 플레이 화면의 `q`는 확인 화면을 한 번 거치고, 거기서는
**`y`만 승낙**한다(`tui.py`의 `is_affirmative`). Enter조차 승낙이 아닌 이유는
화면을 읽지 않고 누른 키가 곧 실행이 되면 확인 단계가 무의미하기 때문이다.

터미널이 실제로 어떤 값을 보내는지 확인해야 하면 `./exam --keydebug`를 쓴다.
두 러너가 같은 `scripts/tui.py` 키 코드를 공유하므로 결과가 동일하다.

## 감시 인디케이터 읽는 법

화면 하단에 감시 상태가 항상 떠 있다. 한 단계가 70ms라 깜빡임으로는 읽을 수
없으므로, **지속적으로 읽히는 정보**로 표시한다.

```
⠹ 감시 중 · 4초 전 갱신 · 명령 로그
```

| 보이는 것 | 의미 |
|---|---|
| 스피너가 돈다 (`⠋⠙⠹⠸…`) | 감시가 살아 움직이는 중 |
| `n초 전 갱신` | 데이터 신선도. 숫자가 계속 커지면 느려지는 중 |
| 끝의 이름 | 지금 수행 중인 감시 단계 |
| `⚠ 감시 오류: …` (빨강) | 고장. 조용히 넘어가지 않는다 |

감시는 **루프 한 바퀴에 단계 하나씩**만 수행한다. 한 번에 몰아서 하면 docker
호출 4개가 연달아 일어나 UI가 240ms 멈추고, 그동안 키 입력이 처리되지 않아
"키가 안 먹는다"처럼 느껴진다. 나눠 돌리면 프리즈가 70ms대로 줄어든다.

## 판정 구조

세 축으로 본다. 이 분리가 이 게임의 핵심이다. 다만 **감시가 보는 것은 앞의 둘**
— DB 상태와 명령 로그 — 뿐이다. 세 번째는 감시로 얻을 수 없어 플레이어에게 직접
묻는다.

| 축 | 무엇을 보는가 | 근거 |
|---|---|---|
| `state` 목표 | **결과** — 목표 상태에 도달했는가 | DB 상태 폴링(2초 주기) |
| `constraints` | **방법** — 어떻게 도달했는가 | `mysql.general_log` 명령 이력 |
| `quiz` 목표 | **이해** — 원인을 알고 고쳤는가 | `exam.py` 채점기 재사용 |

상태만 보면 "범인만 정확히 KILL"과 "전부 쓸어버리기"가 똑같은 정상 복구다.
실무에서는 전혀 다른 이야기이므로 방법도 채점한다.

`quiz`가 따로 있는 이유는 단순하다 — **"원인을 식별했다"는 DB 상태로 증명할 수 없다.**
아무 생각 없이 전부 재시작해도 상태는 정상이 된다.

### 명령 이력을 읽는 방식

`mysql.general_log`는 **CSV 엔진**이라 인덱스가 없어 조회할 때마다 전체 스캔이다.
그래서 엔진은 **읽으면서 곧바로 로그를 비운다**(`SELECT …; TRUNCATE TABLE
mysql.general_log`). 한 접속 안에서 순서가 맞아떨어진다:

1. `Connect` + 클라이언트 배너 질의 + `SET SESSION sql_log_off = 1` → 로그에 남음
2. `SELECT … WHERE user_host LIKE 'dba%'` → 로깅 안 됨, 플레이어 명령 반환
3. `TRUNCATE` → 로깅 안 됨, **1번이 남긴 자기 흔적까지 함께 삭제**

이렇게 하지 않으면 엔진이 **자기가 읽어야 할 로그를 자기가 오염시킨다** — 폴링
접속마다 3행씩 쌓여 10분이면 수천 행이 되고 스캔이 점점 느려진다. 비우면 테이블이
3행 안팎으로 고정되어 스캔 비용이 세션 길이와 무관해진다.

대신 매 조회가 "직전 조회 이후의 새 명령"만 돌려주므로, **엔진이 누적한다**
(`run_watch_step`의 `commands` 단계). 스테이지 판정은 누적된 전체 목록으로 한다.

**`Query`와 `Execute`를 함께 읽는다.** 준비된 구문(prepared statement)은 `Query`
행에 `EXECUTE k USING @pid`만 남기고, **실제로 실행된 문장**은 `Execute` 행에
들어간다(`KILL 999999`). `Query`만 보면 그렇게 친 `KILL`이 `kill_precision`에도
타임라인에도 남지 않는다. 평범한 명령은 `Query`에만 남으므로 중복되지 않고,
`Prepare` 행(`KILL ?`)은 파라미터가 치환되기 전이라 읽지 않는다.

### 사용자 분리

판정의 토대다. `shooting/lab/seed/03-users.sql` 참고.

| 계정 | 역할 | 판정에서의 의미 |
|---|---|---|
| `dba@%` | 플레이어 | 엔진은 `general_log`에서 이 사용자의 명령만 감시 |
| `app@%` | 엔진이 띄우는 범인/피해 세션 | 앱 트래픽처럼 보이되 플레이어 로그를 오염시키지 않음 |
| `repl@%` | replica가 binlog를 받아갈 때 쓰는 계정 | 사람의 명령이 아니라 판정에 잡히지 않음 |
| `root@localhost` | 엔진 자신 (docker exec 소켓) | `user_host`가 달라 자연히 걸러짐 |

`dba`에게 `SHUTDOWN` 권한은 일부러 주지 않는다 — SQL `RESTART`를 막고, "그냥 껐다
켜기" 반사는 `docker restart` 감지로 잡는다.

**명령 로그는 서버마다 따로 있다.** 엔진은 감시 대상 컨테이너를 모두 읽고,
`KILL` 대상과 범인 pid를 `(서버, pid)` 쌍으로 다룬다. pid는 서버마다 따로
매겨지므로, 서버를 함께 보지 않으면 replica의 범인 12번을 근거로 primary의
무고한 12번을 죽인 것이 무사통과한다. 감시 대상은 `setup`과 `objectives`의
`on` 값에서 모은다 — 장애를 넣은 서버와 플레이어가 손대야 할 서버가 다를 수 있다.

### 알려진 한계

감시가 놓치는 자리들이다. **알고 감수하는** 것이지 발견되지 않은 버그가 아니다 —
이 게임은 학습 도구이지 부정 방지 시스템이 아니고, 등급을 속여서 얻는 것도 없다.
다만 스테이지를 만들 때 여기에 기대면 안 된다.

**1. 자기 명령을 로그에서 숨길 수 있다.** `dba`에게는 이후 튜닝 스테이지를 위해
`SYSTEM_VARIABLES_ADMIN`이 있고, 그 권한이면 엔진과 같은 방법
(`SET SESSION sql_log_off = 1`)으로 자기 명령을 로그에서 뺄 수 있다.

**2. 읽기와 비우기 사이에 좁은 유실 창이 있다.** `PLAYER_LOG_SQL`은 한 접속에서
`SELECT` 다음에 `TRUNCATE`를 실행한다. 그 사이(수 ms)에 도착한 명령은 읽히지 않은
채 지워진다. 폴링이 2초마다 돌고 판정 대부분이 누적 목록이 아니라 최종 상태에
기대므로 실해는 거의 없지만, 타임라인에서 명령 한 줄이 빠질 수는 있다.

**이건 고칠 수 없다.** "읽은 지점까지만 지운다"는 방법이 없기 때문이다 — 로그
테이블에는 `DELETE` 자체가 막혀 있다.

```
mysql> DELETE FROM mysql.general_log WHERE event_time < NOW();
ERROR 1556 (HY000): You can't use locks with log tables.
```

남은 선택지는 둘인데 둘 다 비용이 더 크다. **비우지 않고 커서만 들고 다니면**
인덱스 없는 CSV 테이블을 매번 전체 스캔하게 되고 행이 무한히 쌓여 스캔 비용이
세션 길이에 비례해 커진다(지금 구조가 피하려는 것이 정확히 그것이다).
**`log_output = FILE`로 바꿔 파일을 tail 하면** 사용자 분리를 포함한 판정 구조
전체를 다시 써야 한다.

### `setup` — 장애 주입

**setup은 반드시 멱등이어야 한다.** 이전 판의 잔재를 지우고, 데이터를 되돌리고,
그 다음 장애를 주입한다. 그래야 스테이지를 순서 무관하게 다시 플레이할 수 있다.

엔진이 자동으로 해주는 것(스테이지가 선언할 필요 없음):
1. 남아있는 `app` 세션 정리
2. `mysql.general_log` 비우기 — 플레이어 명령 이력의 시작점을 0으로
3. **모든 `state` 목표가 미충족이 될 때까지 대기** — 장애가 실제로 걸린 것을 확인하고 출발한다

세 번째가 없으면, 피해 세션이 아직 잠금을 잡으러 가기 전의 짧은 창에서 타이머가
돌기 시작해 플레이어가 아무것도 안 했는데 클리어돼버린다.

| `type` | 동작 |
|---|---|
| `sql` | `on` 컨테이너에서 root로 실행. **데이터 복원은 여기서 한다** |
| `session` | 분리 세션 1개 기동 |
| `sessions` | 분리 세션 `count`개 기동 |
| `wait_gtid_sync` | `on`이 `source`를 따라잡을 때까지 대기(아래) |

세션 단계의 필드: `on`(기본 `primary`), `user`/`password`(기본 `app`/`app`),
`name`(로그 표시용), `count`(`sessions`만), `culprit`, `idle_seconds`.

`idle_seconds`를 주면 `sql`을 실행한 뒤 그만큼 **접속만 붙잡고 논다**
(`Command=Sleep`). 커넥션 풀 누수를 재현하려면 이게 필요하다 — 기본값인
`mysql -e`는 질의가 끝나면 바로 끊고, `SELECT SLEEP()`은 `Command=Query`로 잡혀
진짜 유휴 커넥션과 구분되지 않는다. 3-1이 이걸 쓴다.

`wait_gtid_sync`의 필드: `on`(따라잡아야 하는 쪽), `source`(기본 `primary`),
`timeout_seconds`(기본 60). 이 단계만 `sql`이 없다 — 대기 자체가 내용이다.
엔진이 자동으로 해주는 3번(모든 `state` 목표가 미충족이 될 때까지 대기)과 다르다.
그 대기는 **장애가 걸렸는지**를 보지만, 이건 장애를 걸기 **전에** 끝나 있어야 하는
초기 동기화다. 없으면 "초기 20만 행이 아직 흐르는 중"과 "장애로 밀렸다"가 섞여
플레이어가 자기가 만들지 않은 지연을 진단하게 된다. 따라잡지 못하면 조용히
넘어가지 않고 setup을 실패시킨다.

### 멱등성을 지키는 관용구

**있을 때만 지우기.** `DROP INDEX`/`DROP COLUMN`은 대상이 없으면 에러라
`IF EXISTS`가 없는 자리에서는 가드가 필요하다. 플레이어가 붙인 이름을 미리 알 수
없으므로 **이름이 아니라 조건으로** 찾아 지우는 편이 안전하다.

```sql
SET @drops := (SELECT GROUP_CONCAT(CONCAT('DROP INDEX `', index_name, '`') SEPARATOR ', ')
  FROM (SELECT DISTINCT index_name FROM information_schema.statistics
        WHERE table_schema='shop' AND table_name='orders'
          AND index_name NOT IN ('PRIMARY','idx_status','idx_customer')) i);
SET @s := IF(@drops IS NULL, 'DO 0', CONCAT('ALTER TABLE shop.orders ', @drops));
PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
```

**바뀌지 않는 UPDATE는 복제되지 않는다.** ROW 포맷에서는 값이 실제로 달라져야
행 이벤트가 생긴다. `SET status='PICKED'`가 이미 `'PICKED'`인 행에 걸리면 아무
이벤트도 남지 않아, 그 이벤트에 기대던 장애가 두 번째 판부터 걸리지 않는다.
복제 스테이지에서 특정 행의 변경을 장애의 방아쇠로 쓴다면 **먼저 다른 값으로
되돌려 두어라**(2-2가 `id=42`를 `'NEW'`로 되돌리는 이유).

**`culprit: true`가 결정적이다.** 이 단계로 뜬 세션의 pid를 엔진이 기억해두고,
나중에 "범인 외 세션을 KILL했는가"를 가려낸다. 표시하지 않으면 `kill_precision`
제약이 성립하지 않는다.

### `vars` — 판마다 숫자를 흔든다

같은 스테이지를 두 번째로 하면 진단이 아니라 **정답 암기**가 된다. `vars`를 두면
파라미터가 판마다 달라진다.

```json
"vars": {
  "lock":    { "type": "span",   "min": 1, "max": 20000, "length": 1000 },
  "victim":  { "type": "int_in", "of": "lock" },
  "victims": { "type": "int",    "min": 5, "max": 10 },
  "mark":    { "type": "choice", "values": ["HOLD", "FROZEN"] }
}
```

| `type` | 만드는 것 | 쓸 수 있는 이름 |
|---|---|---|
| `int` | `min`~`max` 정수 | `{{이름}}` |
| `span` | 길이 `length`인 구간 | `{{이름.from}}`, `{{이름.to}}` |
| `int_in` | 다른 `span` **안의** 정수 | `{{이름}}` |
| `choice` | `values` 중 하나 | `{{이름}}` |

`{{...}}`는 스테이지 전체(문자열이면 어디든 — `sql`, `query`, `expect.value`,
`brief`, `hints`, `debrief`, 문항 텍스트, `count` 같은 숫자 필드까지)에서 치환된다.
`vars`가 없는 스테이지는 아무 영향도 받지 않는다.

**흔드는 것은 숫자이고, 고정하는 것은 장애의 성격이다.** 범인의 종류나 있는 서버가
바뀌면 `quiz` 정답과 `hints`·`debrief`가 전부 거짓이 된다 — 그건 변주가 아니라 새
스테이지다.

**판정 근거가 함께 움직여야 한다.** 잠긴 구간을 흔들면 목표가 보는 행도 그 안으로
따라와야 한다. `{{lock.from + 250}}` 같은 식을 쓰려면 표현식 평가기가 필요한데,
표준 라이브러리만 쓰는 이 저장소에 그건 과한 기계장치다. 그래서 **관계를 타입으로
선언한다** — `int_in`이 그 역할을 하고, 지금 스테이지들에는 이것으로 충분하다.
더 필요해지면 평가기를 만들기 전에 타입을 하나 더 늘리는 쪽을 먼저 검토할 것.

#### 변주를 넣을 때 밟는 함정

- **복원 단계는 뽑을 수 있는 범위 전체를 덮어야 한다.** 지난 판이 건드린 구간은
  이번 판의 구간과 다르다. 1-3은 잠금 구간을 1~20000에서 뽑으면서 복원은
  1~21000을 덮는다(실측 114ms).
- **복원이 목표를 우연히 충족시키지 않게 하라.** 1-3의 `ELT(1 + (id % 4), …)`는
  `id % 4 == 1`인 행을 `'PAID'`로 만드는데, 피해 행이 거기 걸리면 목표가 시작부터
  충족돼 장애가 걸리지 않는다. 그래서 피해 행만 따로 `'NEW'`로 되돌린다.
  (고정 id 500일 때는 `500 % 4 == 0`이라 드러나지 않던 함정이다.)
- **해설과 힌트에 남은 고정 숫자를 잊지 마라.** 3-1의 `debrief`는 "29개가 쌓여
  한도(30)를 먹었다"라고 적혀 있었는데, 그 둘이 변주 대상이 되는 순간 해설이
  거짓말이 된다. 산문도 치환 대상이다.
- **관계가 필요하면 `span`을 쓸 수 있다.** 3-1은 유휴 세션 수가 `max_connections`
  보다 **정확히 하나 적어야** 하는데(관리자 예약 자리), 길이 2짜리 `span`이
  `.from`/`.to`로 딱 그 인접 쌍을 만든다.
- 검증은 `./shoot doctor`가 정의되지 않은 `{{이름}}` 참조, `int_in`이 `span`이
  아닌 것을 가리키는 경우, `span`의 `length`가 범위보다 큰 경우를 잡는다.

#### 변주를 넣지 않은 스테이지

**2-1(복제 구축)에는 `vars`가 없다.** 흔들 수 있는 숫자가 없어서다 — `repl`
비밀번호나 포트를 흔들면 플레이어가 알아낼 방법이 없고, 시드 데이터 행수는 고정이다.
억지로 넣지 않는 편이 낫다.

### `objectives` — 목표

공통: `id`(스테이지 안에서 유일), `type`, `label`(화면 표시).

**`type: "state"`** — DB 상태로 판정.

| 필드 | 설명 |
|---|---|
| `on` | `primary` 또는 `replica` |
| `query` | **단일 스칼라를 돌려주는** SQL. 첫 행 첫 컬럼만 본다 |
| `expect` | `{"op": ..., "value": ...}` |
| `hold_seconds` | 이 시간만큼 **연속으로** 유지돼야 인정 |
| `tolerate_error` | 조회 실패를 '고장'이 아니라 '미충족'으로 읽는다 |

`tolerate_error`는 **조회 대상이 아직 존재하지 않는 것이 정상인 목표**에만 쓴다.
복제를 붙이기 전의 빈 replica에서 `shop.orders`를 세면 당연히 에러인데, 감시는
오류를 삼키지 않는 것이 원칙이라 빨간 `⚠ 감시 오류`가 뜬다. 고장이 아니라 아직
도달하지 않은 상태이므로 오인이다. 기본값은 꺼져 있고, 켜지 않은 목표의 조회
실패는 지금처럼 그대로 드러난다 — 진짜 고장을 숨기지 않기 위해서다.

연산자: `eq` `ne` `lt` `lte` `gt` `gte` `contains` `in`.
`mysql -N -B` 출력은 전부 문자열이지만 엔진이 숫자로 바꿔 비교하므로
`{"op": "eq", "value": 0}`은 `"0"`과 맞는다.

`hold_seconds`를 생략하면 즉시 인정된다. **장애 대응 목표에는 반드시 넣어라** —
없으면 폴링 사이에 스쳐 지나간 순간적 정상 상태로 클리어된다.

**`type: "quiz"`** — 진단 판정. `question`은 `exam.py` 문항 스키마와 같다
(`docs/exam-authoring.md` 참고). `mcq`와 `short`를 지원한다.

`mcq` 보기는 **매 판 섞인다**(순서는 그 판의 시드에서 갈라지므로 `--seed`·`replay`로
같은 판을 열면 순서도 같다). 그래서 `answer`는 시험 쪽 규약대로 **정답을 `0`번에
적으면 된다** — 섞지 않으면 저장소의 모든 문항이 `answer: 0`이라 정답이 항상 1번이
되고, 등급의 '진단 정확도' 항목이 공짜가 된다. '위 모두 정답'처럼 순서가 의미를
갖는 보기가 있으면 `"shuffle": false`로 고정한다(시험 쪽과 같은 탈출구다).

`trigger: {"after_seconds": N}`을 주면 N초 뒤 자동으로 화면이 뜬다.
**생략하면 자동으로 뜨지 않고** 플레이어가 `r` 키로 직접 연다. 상황을 보기도 전에
문항이 튀어나오면 '상황 보고'가 아니라 그냥 퀴즈가 되므로, 자동 발동은
스테이지당 한 개 정도로 아껴 쓴다.

**라인 모드(`--line`)에는 `r` 키가 없다.** 그래서 엔진이 시점을 정한다 —
`trigger`가 있는 문항은 curses와 같은 규칙으로 띄우고, 없는 문항은 `state` 목표를
모두 끝낸 뒤에 묻는다(답하지 않으면 판이 끝나지 않으므로 그때는 물어야 한다).
잘못된 입력은 그 자리에서 다시 묻는다.

비대화형으로 돌릴 때는 출력을 **라인 버퍼링으로 바꾼다**(`ensure_streaming_output`).
stdout이 tty가 아니면 Python이 블록 버퍼링을 쓰기 때문에, 그대로 두면 판이 끝날
때까지 한 글자도 나오지 않는다 — 로그 파일로 넘겨 감시하는 용도가 통째로 죽는다.

비대화형(파이프)으로 돌리면 `input()`을 쓸 수 없으므로 문항을 **건너뛴다.**
건너뛴 문항은 오답이 아니라 채점에서 빠진다 — `target_seconds`가 없을 때 시간으로
감점하지 않는 것과 같은 원칙이다. 대신 진행 표시에 `(건너뜀 — 채점 제외)`로 남아
답한 문항과 구분된다.

### `constraints` — 금지 행동

위반해도 스테이지는 실패하지 않는다. 등급만 내려간다(목숨 없음).

| `detect` | 판정 방법 |
|---|---|
| `container_restart` | 스테이지 시작 시각과 컨테이너 `StartedAt` 비교 |
| `kill_precision` | `general_log`의 `KILL` 대상이 `culprit` 세션인지. `max_extra_kills`(기본 0) 초과 시 위반 |
| `forbidden_command` | 플레이어 명령에 `pattern`(정규식)이 걸리는지. `max_matches`(기본 0) 초과 시 위반 |

`kill_precision`은 `culprit`을 **하나도 표시하지 않은 채** 쓸 수도 있다. 그러면
어떤 `KILL`이든 위반이 되므로 "여기서는 끊는 것 자체가 답이 아니다"를 뜻하게 된다
(4-1이 그렇게 쓴다).

`forbidden_command`는 **"이 명령으로 때우는 것은 복구가 아니다"** 를 산문이 아니라
판정으로 만든다. 3-1의 `SET GLOBAL max_connections`가 그 예다 — 막지는 않는다.
장애 대응으로 한도를 올리는 것 자체는 정당하고, 다만 그게 답이 아니라는 신호를
줄 뿐이다. 값을 **읽는** 것(`SELECT @@max_connections`)은 진단이므로 걸리지 않게
패턴을 좁혀야 한다. 패턴은 `./shoot doctor`가 컴파일해 본다 — 깨진 정규식이 판
도중에 터지면 안 되기 때문이다.

**컴파일된다고 맞는 패턴은 아니다.** doctor가 보는 것은 문법뿐이고, 오탐은
플레이어가 감점당하고 나서야 드러난다. 그래서 새 패턴에는 **걸려야 하는 문장과
걸리면 안 되는 문장을 함께** 테스트에 적는다(`PostgresStageTest`의 `SWEEPS` /
`PRECISE_KILLS`). 특히 부정 전방탐색을 쓸 때 공백은 **전방탐색 안**에서
건너뛰어야 한다 — `\(\s*(?!\d)`처럼 밖에 두면 엔진이 `\s*`를 0글자로 역추적해
공백 위에서 다시 판정하므로, `f( 2108 )`가 "숫자가 아닌 인자"로 잡힌다.
`\((?!\s*\d)`가 맞다.

### 등급

클리어 기본이 C. 아래 넷 중 채운 개수만큼 올라간다 — 4개 S / 3개 A / 2개 B / 0~1개 C.

1. 소요 시간 ≤ `target_seconds`
2. 힌트 0회
3. 금지 행동 위반 0건
4. 진단 문항 전부 정답

**제한 시간은 하드 리밋이 아니다.** 초과해도 계속 플레이할 수 있고 등급만 내려간다.

**기준이 없는 항목은 감점하지 않는다.** `target_seconds`를 두지 않으면 1번을,
`quiz` 목표가 없으면 4번을 그냥 준다. 시간 제한 없는 스테이지(구축형 등)를 만들 수
있어야 하는데, 없다고 해서 S가 구조적으로 불가능해지면 그 선택지가 사라진다.
같은 이유로 `validate_stage`도 `target_seconds`를 필수로 막지 않는다.

### `chapters` — 읽을 곳으로 잇기

읽기(챕터) → 확인(`./exam`) → 겪기(`./shoot`)에서 마지막 축만 앞의 둘과 끊겨
있었다. 장애를 막 겪은 직후가 그 주제를 읽기에 가장 좋은 때이므로, 클리어 화면
끝에 '더 읽을 곳'을 붙인다. 파일명이 아니라 **챕터의 `# 제목`을 읽어 보여준다.**

```
  더 읽을 곳

    - 트랜잭션과 락 (동시성 제어) (02-intermediate/01-transaction-and-locking.md)
    - 스키마 변경 관리 (02-intermediate/06-schema-change-management.md)
```

경로는 **저장소 상대 경로**여야 하고(절대 경로나 `..`는 거부된다), `load_stage`가
**실제 파일이 있는지 확인한다** — 챕터 파일명이 바뀌면 링크가 조용히 썩기 때문이다.

`README.md`의 스테이지 표에도 같은 링크가 있다. 두 곳이 어긋나지 않도록
**테스트가 대조한다**(`test_readme_and_stage_agree_on_chapters`) — 실제로 월드 3
스테이지 셋을 추가하면서 README 표 갱신을 빠뜨린 적이 있다.

4. 관련 챕터를 **스테이지의 `chapters`와 `README.md` 표 양쪽에** 적는다

`tests/test_shooting.py`의 `ShippedStagesTest`가 저장소의 모든 스테이지 정의를

## 랩 구조

`shooting/lab/compose.yaml` — `dbshoot-primary`(3306), `dbshoot-replica`(3307).

두 서버는 **복제가 구성되지 않은 상태**로 뜬다. binlog/GTID만 켜져 있고
`CHANGE REPLICATION SOURCE`는 하지 않는다 — 복제 구성 자체가 구축 스테이지의
과제이기 때문이다. 장애 스테이지는 `setup`에서 필요한 배선을 직접 한다.

`log_output = TABLE` 설정 덕분에 명령 이력이 `mysql.general_log` **테이블**로
들어가고, 파일을 tail 하는 대신 SQL로 조회할 수 있다.

### 복제 스테이지는 많이 플레이할수록 느려진다

2-1과 2-2의 `setup`은 replica의 `shop`을 **지우고 primary의 binlog를 처음부터
재생해 다시 만든다.** 그래서 시작 시각이 primary binlog의 누적 길이에 비례한다.

쓰기가 많은 스테이지를 반복하면 그 누적이 눈에 띄게 커진다 — 3-2는 단건 UPDATE를
1만 건 넘게 돌리므로 한 판에 GTID가 그만큼 늘어난다. 실측으로 3-2·3-3을 여러 번
돌린 뒤 binlog가 **222MB / GTID 148,868개**까지 불어났고, 그 상태에서 2-2의
따라잡기 대기(120초)가 시간 초과로 실패했다. 갓 띄운 랩은 8MB / GTID 22개다.

`./shoot doctor`가 이 누적을 보고 임계치(GTID 5만)를 넘으면 미리 알려준다 —
원인을 모르면 '복제가 고장났나' 하고 엉뚱한 곳을 파게 되기 때문이다. 경고일 뿐이라
다른 스테이지에는 영향이 없고 종료 코드도 바뀌지 않는다.

되돌리는 방법은 랩을 새로 띄우는 것뿐이다.

```bash
./shoot down && ./shoot up     # binlog와 함께 초기화된다
```

primary의 binlog를 함부로 비울 수는 없다 — replica가 그것으로 `shop`을 처음부터
다시 만들기 때문에, 지우면 복제 스테이지가 아예 성립하지 않는다.

### 알아둘 함정

엔진이 `app` 세션을 띄울 때 `mysql --no-defaults`를 쓴다. MySQL 클라이언트의
옵션 우선순위는 **명령줄 > 옵션 파일 > 환경변수**라서, 컨테이너 안
`/root/.my.cnf`의 root 비밀번호가 `MYSQL_PWD`를 이겨버린다. `--no-defaults`가
없으면 `app` 계정 인증이 조용히 실패하고 장애가 주입되지 않는다.

**`DEFINER` 프로시저는 `app` 세션을 숨긴다.** 스토어드 프로시저는 기본이
`SQL SECURITY DEFINER`인데, 그 안을 실행하는 동안 `information_schema.processlist`의
`user`가 **정의자(root)** 로 보고된다. 엔진은 `user='app'`으로 세션을 추적하므로,
부하 생성용 프로시저를 그냥 만들면 세션이 잡히지 않아 기동 대기가 20초를 헛돌고
판이 끝나도 정리되지 않아 다음 판까지 살아남는다. 부하 프로시저는 반드시
**`SQL SECURITY INVOKER`** 로 만든다.

**`DELIMITER`는 줄 단위 명령이다.** `sql` 단계는 `mysql -e`로 실행되는데,
`DELIMITER`는 클라이언트가 줄 단위로 해석한다. 프로시저를 만들 때 한 줄로 붙이면
`;`에서 잘려 문법 오류가 난다. JSON 문자열 안에 `\n`을 넣어 `DELIMITER //`와
`DELIMITER ;`가 각각 자기 줄을 갖게 해야 한다.

**엔진의 장부질은 binlog에 남기지 않는다.** 명령 로그를 비우는
`TRUNCATE TABLE mysql.general_log`는 그냥 두면 binlog에 실려 **replica에서도
실행된다.** 감시는 primary 로그를 먼저 읽고(=비우고) replica를 나중에 읽으므로,
그 사이 복제가 전달한 TRUNCATE가 replica의 로그를 지워 플레이어가 거기서 친
명령이 매 주기 증발한다. 그래서 `NO_BINLOG`(`SET SESSION sql_log_bin = 0`)를
앞에 붙인다. 반대로 **스테이지의 `sql` 단계는 복제되어야 한다** — 2-2의 센티널
행이 replica에 도달하는 것이 판정의 근거이기 때문이다.

**`DELIMITER`를 `sql` 단계의 맨 앞에 두지 마라.** 엔진이 SQL 앞에
`SET SESSION sql_log_off = 1; `을 붙이므로, 맨 앞에 있으면 그 문장과 **같은 줄**이
되어 클라이언트가 알아보지 못한다(문법 오류로 setup이 실패한다). 앞에 다른 문장이
있거나 문자열이 개행으로 시작하면 된다 — 3-3이 `"\nDELIMITER //…"`로 시작하는 이유다.

**디스크 풀은 전용 볼륨에서만 재현한다.** 주 데이터 볼륨을 채우면 InnoDB가 손상돼
`./shoot down -v` 말고는 되돌릴 방법이 없어질 수 있다. 3-3은 compose의 32MB tmpfs
(`/var/lib/dbshoot-audit`)에 `DATA DIRECTORY`로 테이블 파일만 올려두므로, 그 테이블
쓰기만 실패하고 나머지 데이터베이스는 멀쩡하다. 알아둘 것 셋:

- **`ERROR 1114`는 `CONTINUE HANDLER`로 잡아도 `CALL` 밖으로 올라온다.** 그래서
  "가득 찰 때까지 넣기"로는 setup을 만들 수 없다. `INNODB_TABLESPACES.FILE_SIZE`
  합계를 보며 볼륨 크기에 조금 못 미친 곳에서 멈춰야 한다.
- **가득 차도 단건 INSERT는 성공한다.** 롤백으로 생긴 내부 빈 페이지를 재사용하기
  때문이다. 파일을 늘려야 하는 대량 쓰기만 실패하므로, 증상은 "배치가 실패한다"로
  써야 정확하다.
- **tmpfs는 컨테이너를 다시 띄우면 비워지는데 데이터 딕셔너리는 남는다.** 그 상태의
  테이블은 조회 시 `ERROR 1812`가 나지만 `DROP TABLE IF EXISTS`는 성공하므로,
  setup 첫 단계에서 그것으로 정리하면 재기동 직후에도 멱등하다.

**로그를 켜기 전에 접속한 세션은 켠 뒤에도 기록되지 않는다.** `slow_query_log`를
`SET GLOBAL`로 켜도, 그 전부터 열려 있던 접속의 질의는 슬로우 로그에 남지 않는다
(실측). 그래서 '로그를 켜게 하는' 스테이지에 부하 세션을 **미리 띄워두면 안 된다** —
플레이어가 무엇을 해도 그 세션의 질의는 잡히지 않아 목표가 영영 충족되지 않는다.
4-2가 부하 세션 없이, 플레이어가 스스로 느린 질의를 흘려 넣어 확인하도록 만들어진
이유다. 실무의 커넥션 풀이 겪는 문제이기도 해서 그대로 debrief의 교훈이 됐다.

**구축형(`kind: build`)은 장애를 주입하지 않는다.** 대신 '준비되지 않은 상태'를
만들고, 목표가 곧 갖춰야 할 것이 된다. `_wait_for_incident`가 요구하는 '모든 `state`
목표가 미충족'은 그대로 지켜야 하므로, setup은 **설정을 되돌려 끄는 일**을 한다.

**스스로 풀리는 장애는 '지금 상태'로 잴 수 없다.** 데드락은 InnoDB가 감지해
한쪽을 롤백시키므로 순간적으로 끝나고, `data_lock_waits` 같은 '지금 대기 중'
화면에는 아무것도 남지 않는다. 1-2는 발생할 때마다 로그 테이블에 한 줄씩 남기고
**마지막 발생 이후 경과 시간**(`TIMESTAMPDIFF(SECOND, MAX(at), NOW())`)으로
판정한다 — 엔진이 시계열을 다루지 않아도 '멎었는가'를 잴 수 있다. 이때 그 로그
테이블은 `setup`에서 **반드시 다시 만들어야** 한다. 지난 판의 기록이 남아 있으면
이번 판이 아직 아무것도 내지 않은 시점에 '마지막 발생이 오래 전'으로 읽혀 목표가
시작부터 충족된다.

**프로시저 안에서는 `processlist.time`이 0에 머문다.** 그 값은 지금 실행 중인
**문장**의 경과 시간이라, 루프 안에서 짧은 질의를 반복하면 매번 초기화된다(실측).
판정을 `time`으로 잡을 수 없을 뿐 아니라, 플레이어가 배울 진단 경로
('`Time`이 큰 줄을 찾아라')도 통째로 깨진다 — 1-1을 프로시저로 만들었다가
이 때문에 단일 문장으로 다시 썼다. **오래 걸리는 것을 보여주려면 오래 걸리는
문장 하나**를 써야 한다. 반대로 잠금·트랜잭션을 오래 붙잡는 것이 목적이라면
`innodb_trx.trx_started`(3-2)나 `command='Sleep'`(3-1)처럼 다른 지표를 본다.

**`setup`의 `sql` 단계는 30초 안에 끝나야 한다.** `mysql()`의 기본 타임아웃이라
넘기면 `TimeoutExpired`가 그대로 올라와 판이 시작조차 못 한다. 부하를 미리 쌓아두는
단계가 특히 걸리기 쉽다 — 3-2의 갱신 프로시저는 실측 약 1,000건/초라 12,000건을
넣는다(처음에 30,000건으로 썼다가 이 타임아웃에 막혔다). 더 큰 부하가 필요하면
`sql` 단계 대신 `session` 단계로 띄워 백그라운드에서 돌게 한다.

**커넥션을 고갈시키는 스테이지는 한 자리를 남겨야 한다.** MySQL은
`CONNECTION_ADMIN`/`SUPER` 계정을 위해 한도 **바깥에 한 자리**를 예약하는데,
그 한 자리를 플레이어(`dba`)와 엔진(`root@localhost`)이 **함께** 노린다.
`max_connections`를 전부 채우면 둘 중 하나가 못 들어와 판이 성립하지 않는다.
3-1은 `max_connections - 1`만 채운다 — 남은 정규 한 자리를 엔진이, 예약 자리를
플레이어가 쓴다. 실측으로 확인했다(엔진 폴링·플레이어 접속 각 0/12 실패,
컨테이너 healthy, 새 `app` 접속은 `ERROR 1040`).

한 가지 더: 이 스테이지를 하고 나면 랩의 `max_connections`가 낮아진 채로 남는다.
`SET GLOBAL`은 컨테이너를 다시 띄우면 사라지고 다른 스테이지는 세션을 12개
넘게 쓰지 않으므로 실해는 없지만, 새 스테이지가 서버 설정을 바꾼다면 **그 설정을
되돌리는 것도 자기 `setup`의 몫**이라는 점을 기억해 둘 것(3-1의 첫 단계가 그렇다).

## 성능 스테이지를 쓸 때 (실측으로 배운 것)

**저장 프로시저 안의 문장은 statement digest 에 개별 항목으로 잡히지 않는다.**
`events_statements_summary_by_digest` 에는 바깥의 `CALL ...` 한 줄만 남는다
(측정: 8세션이 프로시저로 25초간 돌렸는데 `%member%` digest는 0건, 같은 질의를
클라이언트에서 직접 치면 즉시 집계됨). 이 저장소는 부하 생성에 프로시저를
쓰도록 규정하고 있으므로(세션 추적 때문), **digest 를 진단 경로로 삼는 스테이지는
성립하지 않는다.** `SHOW PROCESSLIST` 는 프로시저 안에서 실행 중인 문장을
보여주므로 그쪽을 쓴다.

**부하 질의가 무엇을 읽는지가 실행 계획을 바꾼다.** 4-3을 처음 쓸 때 부하를
`SELECT COUNT(*) ... WHERE code = <숫자>` 로 뒀더니 인덱스만으로 답이 나와
**커버링 인덱스 풀스캔**(`type=index`, `key=idx_code`)이 됐다. 가르치려던 지문인
`key=NULL` 이 나오지 않아 힌트와 해설이 **플레이어가 보지 못할 화면을 설명하는**
상태였다. 인덱스에 없는 컬럼(`MAX(name)`)을 읽게 바꾸니 `type=ALL, key=NULL` 이
나왔다.

일반화하면 — **스테이지가 설명하는 화면을 실제로 띄워 보고 써라.** 계획을
말로 예측하면 틀린다.

**회복 판정은 누적이 아니라 최근 구간으로 본다.** 부하 세션이 자기 소요 시간을
로그 테이블에 남기게 하고 `WHERE at > NOW(6) - INTERVAL 15 SECOND` 로 본다.
누적 평균으로 판정하면 장애 구간이 영원히 섞여 들어와 회복이 드러나지 않는다.
행이 없을 때를 `COALESCE(..., 999)` 로 막아야 부하가 끝난 뒤 저절로 충족되지
않는다.

**계획은 방법이 아니라 결과로 판정한다.** `EXPLAIN FORMAT=JSON` 이 한 컬럼
문자열을 돌려주므로 `expect: {op: "contains", value: "\"access_type\": \"ref\""}`
로 본다. 특정 `ALTER` 를 확인하는 대신 **계획이 인덱스를 타는가**를 보므로 어떤
경로로 고쳤든 통과한다.

## 다른 DBMS 추가

스테이지 JSON에 `dbms` 필드가 있고, PostgreSQL 랩이 **compose 프로파일 뒤에**
준비돼 있다. 기본 `./shoot up`은 지금까지와 똑같이 MySQL만 띄운다 — MySQL
스테이지만 하는 사람이 이미지 내려받기와 기동 시간을 치를 이유가 없다.

```bash
./shoot up --with-postgresql     # PostgreSQL 랩까지 함께
```

`./shoot doctor`가 `psql` 클라이언트와 PostgreSQL 랩 상태를 함께 알려준다.
둘 다 **없어도 점검은 실패하지 않는다** — MySQL 스테이지를 막을 이유가 없다.

### 감시 소스 — 판정 구조가 그대로 옮겨온다

판정 전체가 "명령 이력을 SQL로 조회하고 사용자로 가른다"에 얹혀 있다.
PostgreSQL은 명령 이력을 테이블이 아니라 로그 파일로 남기므로, contrib 모듈
**`file_fdw`로 CSV 로그를 외부 테이블처럼 읽는다**(`pg-seed/03-logview.sql`의
`command_log`).

| MySQL | PostgreSQL |
|---|---|
| `mysql.general_log` (CSV 엔진) | CSV 로그 + `file_fdw` 외부 테이블 `command_log` |
| `user_host LIKE 'dba%'` | `user_name = 'dba'` |
| `command_type IN ('Query','Execute')` | `message LIKE 'statement:%'` |
| `TRUNCATE TABLE mysql.general_log` | `truncate -s 0 <로그파일>` (docker exec) |
| `SET SESSION sql_log_off = 1` | **불필요** — 엔진은 `postgres`로 접속하므로 `user_name` 필터에 자연히 걸러진다 |

마지막 줄이 MySQL보다 단순한 부분이다. MySQL에서는 엔진이 자기 흔적으로 자기가
읽을 로그를 오염시켜서 `sql_log_off`가 필요했지만, PostgreSQL은 사용자 이름만으로
갈린다.

**로그 파일명 함정**: `log_filename`을 `pg`로 줘도 `csvlog`가 `.csv`를 덧붙여
실제 파일은 `pg.csv`가 된다. 외부 테이블의 `filename`이 어긋나면 감시가 조용히
아무것도 읽지 못한다(테스트가 이 경로를 대조한다).

### 엔진은 target 하나로 갈린다

**컨테이너가 곧 벤더다.** `primary`/`replica`는 MySQL, `postgres`는 PostgreSQL이므로
`target` 이름만으로 어느 DBMS인지 정해진다(`TARGET_VENDOR`). 덕분에 엔진의 I/O
함수들은 **시그니처를 바꾸지 않고** 내부에서만 갈라지고, 호출부는 자기가 어느
DBMS를 상대하는지 알 필요가 없다.

스테이지는 `dbms`만 적으면 된다. 생략한 `on`/`source`는 **불러올 때 한 번**
`normalize_targets()`가 채운다(`default_target()`). 기본값을 읽는 쪽마다 풀면
`.get("on", "primary")`가 흩어져 한 군데만 놓쳐도 조용히 MySQL primary로 간다.
`validate_stage()`가 `dbms`와 대상 서버가 어긋나는 스테이지를 거른다.

PostgreSQL 스테이지를 고르면 랩이 떠 있는지 먼저 확인하고
`./shoot up --with-postgresql` 을 안내한다 — 걸러 주지 않으면 setup이
docker exec 실패로 무너지고 원인이 드러나지 않는다.

### MySQL과 달라지는 것들 (전부 실측)

| | MySQL | PostgreSQL |
|---|---|---|
| 엔진 질의 | `mysql -N -B -e` | `psql -X -qtA -F'\t' -v ON_ERROR_STOP=1 -c` |
| 세션 종료 | `KILL <pid>` (문장) | `pg_terminate_backend(<pid>)` (**함수**) |
| 세션 목록 | `information_schema.processlist` | `pg_stat_activity` |
| 주입 세션 비밀번호 | `MYSQL_PWD` | `PGPASSWORD` |
| 로그 비우기 | `TRUNCATE TABLE` | 파일 `truncate -s 0` |

**psql은 한 `-c` 안의 여러 문장을 하나의 트랜잭션으로 묶는다**(MySQL은 문장마다
자동 커밋). 문장별 커밋이나 트랜잭션 블록에서 못 도는 명령이 필요하면 `setup`의
`sql` 단계를 나눠라 — 엔진이 이미 지원하는 표현이라 별도 장치가 없다.

**주입 세션은 `-h 127.0.0.1`로 TCP를 강제한다.** 유닉스 소켓으로 가면 로컬 신뢰
인증에 걸려 **PGPASSWORD 없이도 붙어버리고**, 계정을 틀려도 알아채지 못한다.
MySQL 쪽 `--no-defaults`와 같은 자리의 함정이다.

**읽기와 비우기를 한 번의 `docker exec`로 묶는다.** 두 번으로 나누면 그 사이에
들어온 플레이어 명령이 통째로 사라진다(MySQL 쪽은 두 문장이 한 접속 안에서
이어져 창이 훨씬 좁다).

### 판정의 두 구멍 (PostgreSQL에만 있다)

MySQL에서는 생기지 않던 것이라 스테이지를 쓸 때 알고 있어야 한다.

**1. 파싱 오류는 감시에 남지 않는다.** `general_log`는 클라이언트가 보낸 것을
무조건 남기지만 PostgreSQL은 그렇지 않다. 실측 결과 정확히 **파싱 오류만**
빠진다:

| 플레이어가 친 것 | 잡히는가 |
|---|---|
| `SELECT 1` | 잡힘 |
| `SELECT * FROM nope` (없는 테이블) | 잡힘 |
| `ALTER SYSTEM ...` (권한 오류) | 잡힘 |
| `KILL 999999` (PG 문법이 아님) | **놓침** |

**2. pid를 적지 않는 쓸기가 보이지 않는다.**

```sql
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE ...
```

`parse_kill_targets()`가 뽑는 것은 문장에 적힌 숫자뿐이라 이 형태는 잡히지
않는다. MySQL에는 pid를 적지 않고 쓸어버리는 문법이 없어 생기지 않던 구멍이다.
이걸 감점 대상으로 삼으려면 스테이지에서 `forbidden_command`로 그 모양을 직접
막아라 — `kill_precision`은 "범인만 골라 죽였는가"를 보는 도구지 쓸기
탐지기가 아니다.

### 랩 구조의 비대칭 하나

MySQL 랩은 `shop` 데이터베이스를 쓰지만 PostgreSQL 랩은 기본 `postgres`
데이터베이스의 `public` 스키마를 쓴다(`PG_PLAYER_DB`). 스테이지 SQL을 두 벤더로
옮길 때 이 이름 차이를 그대로 두면 된다.

### 선택 화면

`group_by_dbms()`가 DBMS로 묶고, 화면은 **DBMS → 월드 → 스테이지**로 내려간다.
DBMS가 하나뿐이면 그 단계를 건너뛰므로, 스테이지가 전부 MySQL인 동안에는 화면이
예전과 똑같다(테스트가 이 조건을 고정한다). `--list`의 머리글도 같은 규칙이다.

`dbms`를 적지 않은 스테이지는 MySQL로 본다 — 기존 스테이지가 그렇게 쓰여 있고,
그게 PostgreSQL로 새면 없는 랩에 붙으러 간다.

### 첫 PostgreSQL 스테이지가 무엇을 골랐나

`pg-1-1-idle-in-transaction`. MySQL 스테이지를 번역하지 않고 **PostgreSQL에만
있는 것**을 골랐다 — `idle in transaction`, 그리고 `pg_cancel_backend`가
그 상태에 무력하다는 사실이다.

실측으로 확인한 교육 요점:

```
SELECT pg_cancel_backend(2108);   -- t 를 돌려준다
                                  -- 세션은 여전히 idle in transaction, 대기 3건 그대로
SELECT pg_terminate_backend(2108);  -- 이제 끊긴다. 대기 0, 결제 커밋
```

반환값 `t`는 '해결됐다'가 아니라 '신호를 보냈다'는 뜻이다. 돌고 있는 질의가
없으면 취소할 것도 없다. MySQL의 `KILL QUERY` / `KILL CONNECTION` 이 같은
자리의 구분이지만, MySQL 스테이지에서는 범인이 늘 무언가를 **하고 있어서**
이 차이가 드러나지 않는다.

**스테이지 id에 `pg-` 접두사를 붙였다.** 월드 번호는 벤더별로 다시 시작하므로
(PostgreSQL 월드 1의 첫 스테이지도 `1-1`이다) 접두사가 없으면 진행 기록과
노트 디렉터리에서 MySQL 쪽과 구분되지 않는다.

### 피해자 세션은 서로 막지 않게 해야 한다

처음에는 결제 세션들이 전부 같은 행을 노리게 썼다. 그랬더니 **서로도 막아서**
`pg_blocking_pids()`가 범인 하나가 아니라 사슬 전체를 지목했다(실측: 3개 세션에
지목된 범인이 6개). 잠금 사슬 자체는 현실적이지만, `kill_precision`이 걸린
판에서는 **도구가 범인이라고 알려준 세션을 끊었다가 감점되는** 부당한 함정이
된다. 세션마다 다른 행을 고르게 하면 지목이 하나로 좁혀진다.

일반화하면: 판정이 "정확히 하나를 골라라"라고 요구할 때는, 플레이어가 쓸 진단
도구가 실제로 **하나만 가리키는지** 확인해야 한다.

### PostgreSQL 스테이지를 쓸 때

- `on`은 생략해도 된다. `dbms: "postgresql"` 이면 `normalize_targets()`가
  `postgres`로 채운다.
- **범인 세션은 `idle_seconds`가 `target_seconds`보다 길어야 한다.** 짧으면
  판이 끝나기 전에 저절로 풀려 플레이어가 아무것도 하지 않았는데 클리어된다.
- `BEGIN; UPDATE ...` 를 `idle_seconds`와 함께 주면 `idle in transaction`이
  된다 — psql이 stdin을 기다리는 동안 트랜잭션이 열린 채로 남는다.
- 세션을 끊는 스테이지라면 **`forbidden_command`로 쓸기를 함께 막아라.**
  `kill_precision`은 pid가 적히지 않은 종료를 볼 수 없다(위 "판정의 두 구멍").
  `(?i)pg_terminate_backend\s*\(\s*(?!\d)` 가 숫자가 아닌 인자만 걸러내므로
  정확한 복구는 통과한다 — 패턴은 **양방향으로** 확인해야 한다.
