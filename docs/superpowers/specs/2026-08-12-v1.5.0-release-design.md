## 1. #90 — mysql·oracle 실습 예제 복원

### 1.1 현행 결함 (이슈 기술보다 한 단계 나쁘다)

`02-intermediate/04-backup-recovery-strategies.md`의 94~130행이 통째로 `<!-- dbms:postgresql -->` 안에 있다. 이슈 #90은 "실습 예제 절이 사라진다"까지 적었지만, 실제로는 **125~128행의 MySQL PITR 설명과 `mysqlbinlog` 예시도 같은 블록 안에 갇혀 있다.**

````
125  MySQL의 PITR은 "가장 가까운 전체 백업 복원 → 그 이후 binlog를 …" 동일한 개념으로 수행한다.
127  ```bash
128  mysqlbinlog --stop-datetime="2026-07-15 14:29:00" binlog.000123 | mysql
129  ```
130  <!-- /dbms:postgresql -->
````

`filter_lines`는 줄 범위만 본다. 따라서 이 문장들은 **PostgreSQL 독자에게만 보이는 MySQL 설명**이고, mysql 브랜치 독자는 실습 절뿐 아니라 자기 벤더용 PITR 안내까지 잃는다.

### 1.2 범위 측정

세 벤더로 필터한 뒤 `check_structure`를 돌린 결과 — 이 부류는 오늘자로 **이 파일 하나, 두 벤더가 전부**다.

```
postgresql: 0건
mysql:      1건   02-intermediate/04-backup-recovery-strategies.md: `## 실습 예제` 절이 없거나 순서가 어긋난다
oracle:     1건   (동일)
```

### 1.3 새 구조 — 공통 시나리오 + 벤더별 완전 절차

```
## 실습 예제 — 특정 시점 복구(PITR)          ← 마커 밖
시나리오 문단                                 ← 마커 밖, 벤더 중립 문구로 재작성

<!-- dbms:postgresql -->
### PostgreSQL — base backup + WAL 재생
<!-- /dbms:postgresql -->

<!-- dbms:mysql -->
### MySQL — 전체 백업 복원 + binlog 재적용
<!-- /dbms:mysql -->

<!-- dbms:oracle -->
### Oracle — RMAN 불완전 복구
<!-- /dbms:oracle -->

복구 훈련 관점의 공통 마무리 문단              ← 마커 밖
```

이슈의 2번안(명령어만 벤더별로 가르고 단계 서술은 공유)을 택하지 않은 이유: PITR은 **단계 구성 자체가 벤더마다 다르다.** PostgreSQL은 `recovery.signal` + promote, Oracle은 `OPEN RESETLOGS`라는 되돌릴 수 없는 분기가 있고, MySQL은 복원 기준점을 binlog 좌표로 잡는다. 단계를 공유하면 서술이 어느 벤더에도 정확하지 않은 최소공배수로 수렴한다.

### 1.4 각 절의 내용

- **PostgreSQL** — 현행 99~123행을 그대로 옮긴다. 내용 변경 없음.
- **MySQL** — 125~128행을 완전한 절차로 확장한다. 전체 백업 복원 → `SHOW BINARY LOGS`로 재적용 시작 좌표 확인 → `mysqlbinlog --start-position … --stop-datetime … | mysql`. GTID가 켜진 환경에서 `--skip-gtids`가 필요할 수 있다는 점을 한 줄 주의로.
- **Oracle** — 신규. `STARTUP MOUNT` → `RESTORE DATABASE` → `RECOVER DATABASE UNTIL TIME` → `ALTER DATABASE OPEN RESETLOGS`. **RESETLOGS는 새 인카네이션을 만든다 — 10g 이후 RMAN은 인카네이션을 인식해 이전 백업으로도 복구할 수 있지만 절차가 복잡해지므로, 개방 직후 전체 백업을 다시 받아야 한다**는 점을 주의로.

시나리오 문단은 현행 "매일 새벽 물리 백업 + **WAL 아카이빙**"에서 `WAL`을 걷어내고 "연속 로그 아카이빙"으로 바꾼다 — 마커 밖에 놓이므로 세 벤더가 함께 읽는다.

### 1.5 체크리스트

148~150행의 PostgreSQL 전용 항목에 나머지 두 벤더의 쌍을 맞춘다.

```
- [ ] PITR의 원리(기준 백업 + 연속 로그 아카이빙)를 설명할 수 있다.   ← 공통, 유지
<!-- dbms:postgresql --> …PostgreSQL에서 특정 시점까지 PITR 복구 절차를 수행할 수 있다.
<!-- dbms:mysql -->      …MySQL에서 binlog 재적용으로 PITR을 수행할 수 있다.
<!-- dbms:oracle -->     …Oracle에서 RMAN 불완전 복구를 수행하고 RESETLOGS 이후 조치를 안다.
```

### 1.6 딸림 점검 (정책의 「사람 몫」 항목)

- **치트시트** — `02-intermediate/09-commands-cheatsheet.md:66`에 3벤더 PITR 행이 **이미 있다** (`recovery_target_time` / `mysqlbinlog --stop-datetime` / `RECOVER … UNTIL TIME`). 62·64행에 논리·물리 백업 행도 있다. 본문에서 `OPEN RESETLOGS`·`SHOW BINARY LOGS`를 새로 도입하는 만큼 행 추가 여부를 판단한다.
- **용어집** — `appendix/glossary.md`에 `불완전 복구(incomplete recovery)`·`RESETLOGS` 반영 여부를 판단한다.
- **문제은행** — `exams/02-intermediate/04-backup-recovery-strategies.json`은 9문항(neutral 6 / pg 1 / mysql 1 / oracle 1)으로 벤더 균형이 이미 맞다. 새 절차와 어긋나는 문항이 없는지 내용만 확인한다.

## 2. 회귀 가드 — 검사기에 벤더 필터

### 2.1 검사기

```python
def check_structure(root, dbms=None):
    """dbms가 주어지면 filter_dbms.filter_lines를 통과시킨 뒤 heading을 뽑는다."""
```

`filter_dbms.filter_lines`를 재사용하는 것이 요점이다. `generate-branch.sh`도 `reading.py`도 같은 함수를 부르므로, 검사 결과가 실제 벤더 브랜치와 **정의상** 어긋날 수 없다. 검사기가 필터를 자체 구현하면 "검사는 통과했는데 브랜치는 깨진" 상태가 가능해진다.

`main(argv)`에 `--dbms {postgresql,mysql,oracle}`를 추가하고, 출력의 `[structure]` 라벨에 벤더를 표기한다. 릴리스 전에 사람이 직접 돌릴 수 있는 통로다.

### 2.2 스위트

`tests/test_check_content.py`의 `ShippedContentTest`에 세 벤더 검사를 추가한다.

```python
def test_each_vendor_view_keeps_the_four_section_shape(self):
    self._skip_on_a_vendor_branch()
    for dbms in ("postgresql", "mysql", "oracle"):
        with self.subTest(dbms=dbms):
            self.assertEqual(check_content.check_structure(REPO_ROOT, dbms), [])
```

`_skip_on_a_vendor_branch`는 **그대로 둔다.** 필터된 뷰를 또 필터하는 것은 무의미하고, CI 트리거가 `push: branches: [main]`이라 벤더 브랜치에서는 어차피 돌지 않는다. 이 가드가 값을 내는 자리는 `main`이다.

단위 테스트는 픽스처에 "절 하나가 통째로 한 벤더 마커 안"인 챕터를 만들어, 그 벤더 뷰에서는 통과하고 나머지 둘에서는 위반을 보고하는지 확인한다.

### 2.3 검증 방식

이 저장소가 최근 커밋(`9634706`)에서 쓴 **mutate-and-watch-red**를 따른다. 가드를 붙인 상태에서 §1의 수정을 되돌려 빨개지는 것을 실제로 보고, 복원해 초록으로 돌아오는 것을 본다. 가드가 무엇을 잡는지 보지 않은 채 초록인 것은 아무것도 증명하지 않는다 — `ClientCheckSymmetryTest`가 몇 달간 그랬다.

표준 라이브러리만 쓰므로 CI 원칙에 저촉되지 않는다.

「알려진 한계」에 적을 것 — 전부 실측·문서 근거가 있고 지어내지 않는다.

- East Asian Ambiguous 글리프(`─ │ ━ • · ◆`)를 2칸으로 그리는 터미널 설정에서 256행이 80칸을 넘는다 (리플로우 작업 전 853행에서 줄어든 값). `tui.cwidth`의 저장소 전역 가정이고 이식 가능한 탐지 수단이 없다.
- **학습 점검(`exam`) 화면은 아직 자체 키 계약을 쓴다** — `q`는 시험만 끝내고 `Esc`는 무반응. `Q`가 닿지 않는 유일한 화면.
- 장애 대응 게임 **진행 중** 서버 선택 화면은 `Q`가 막혀 있다(컨테이너가 뜬 채 남으므로). `Esc`로 취소한다.
- PostgreSQL 판정의 두 구멍 — 파싱 오류가 감시에 남지 않고, pid를 적지 않는 `pg_terminate_backend` 쓸기를 `kill_precision`이 못 잡는다.
- 스테이지 벤더 편중 MySQL 13 / PostgreSQL 1 / Oracle 0 (#79).
- 치트시트 행·용어집 반영·문제은행 내용의 최신성은 여전히 사람 몫이다 (`check_content.py`는 판정 가능한 것만 본다).
- **Oracle RMAN 절차는 실행 검증이 아니라 문서 근거로 작성됐다** — shooting 랩에는 MySQL과 PostgreSQL만 있다.

### 스테일 브랜치 (10단계)

`git cherry origin/main origin/<branch>`가 일곱 개 모두에 대해 전부 `-`(main에 동등 커밋 있음)를 찍는다. squash·rebase 머지 후 남은 것들이다.

```
Ahngbeom/issue-95  Ahngbeom/issue-96  Ahngbeom/reading-exam-handoff
Ahngbeom/shooting-infra  Ahngbeom/dbms-by-branch  Ahngbeom/kube-oracle-mysql-operator
feature/tui-exam
```

**태그가 찍힌 뒤에** 지운다. `v1.5.0`이 해당 커밋들을 영구히 붙잡으므로 도달 불가 커밋이 생기지 않는다. 삭제 전 건별로 제시하고 확인받는다.

## 5. 위험

- **4·9단계는 자동화되지 않는다.** 정책이 "사람 몫"으로 명시한 항목이고, CI에도 없다(4단계는 docker 의존, 9단계는 발행된 태그를 실제로 fetch해야 함).
- **Oracle RMAN 절차를 실행 검증할 수 없다.** 랩에 Oracle이 없다. 문서 근거로 쓰고 「알려진 한계」에 밝히는 것이 유일하게 정직한 처리다.
- **6단계는 되돌릴 수 없다.** `generate-branch.sh`가 `git worktree add -B "$target" main`으로 벤더 브랜치를 매번 리셋하므로 `--force-with-lease` push가 정상 동작이지만, 원격 히스토리를 덮어쓴다. 실행 전 확인받는다.
