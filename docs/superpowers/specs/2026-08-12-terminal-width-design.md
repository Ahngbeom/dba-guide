# 챕터 읽기 터미널 너비 대응 — 설계

작성일: 2026-08-12
관련 이슈: [#96 챕터 읽기 터미널 너비 호환/대응](https://github.com/Ahngbeom/dba-guide/issues/96)

## 배경

이슈 #96은 제목만 있고 본문·라벨·댓글이 비어 있다. 그래서 증상을 코드에서 직접
실측했다. 챕터 31개 전량을 `markdown_render.render()`로 폭을 바꿔 가며 렌더한 결과다.

| 항목 | 결과 |
|---|---|
| 폭 초과 줄 (`tui.cwidth` 기준, 40/60/80/100칸) | **0건** |
| 코드 펜스 강제 개행 (토큰 중간 절단) | 80칸 **6%**, 60칸 **25%**, 40칸 **49%** (코드 줄 1,867개 기준) |
| 표 자연폭 | 표 **44개**, 중앙값 **130칸**, 최대 **192칸** |
| 자연폭이 화면을 넘어 압축되는 표 | 80칸에서 **36/44**, 60칸에서 40/44, 40칸에서 43/44 |
| `_MIN_COL`(4) 하한 충돌 | 어느 폭에서도 **0건** |
| 제목 잘림 (`_emit_heading`의 `fit`) | 제목 322개, 최대 폭 73칸 → 40·60칸에서 **꼬리가 소실** |
| 읽는 중 창 크기 변경 | **무대응** — 사전 렌더 후 `less`에 넘기므로 재배치 불가 |

세 가지가 이 표에서 드러난다.

첫째, **폭 보장 자체는 지켜지고 있다.** 렌더러가 폭을 넘기는 줄은 한 줄도 없다.
이슈는 "폭을 넘는다"가 아니라 "폭이 좁거나 바뀌면 레이아웃이 무너진다"이다.

둘째, **좁은 터미널만의 문제가 아니다.** 표 자연폭 중앙값이 130칸이라 기본 80칸
터미널에서도 44개 중 36개(82%)가 이미 압축된다. 40칸에서 `PostgreSQL`이
`PostgreSQ`/`L`로 쪼개지고 `localhost:` / `1521/XEPDB` / `` 1` `` 처럼 셀 내용이
토큰 중간에서 끊긴다. 열이 0폭이 되는 일은 없지만(`_MIN_COL` 충돌 0건) 그 위에서
이미 뭉개진다.

셋째, **제목만 진짜로 데이터를 버린다.** `_emit_fence`는 `while` 루프로 긴 줄을
이어 붙여 손실이 없는데, `_emit_heading`은 `fit(text, width)`로 잘라낸다. 40칸에서
`### 시나리오: "프로덕션 DB CPU 100%, 애플리케이션 전면 5xx" (PostgreSQL 기준)`가
`· 시나리오: "프로덕션 DB CPU 100%, 애플`로 끝난다. 렌더러의 유일한 실제 데이터
손실이다.

**이것은 실수가 아니라 근거가 적힌 결정이다.** 현재 주석이 그 근거를 남기고 있다.

> 제목은 접지 않고 자른다 — 접힌 제목은 본문과 구분이 안 된다. 자르지 않으면
> `less` 가 접어서 같은 결과가 되고, 폭 회귀 테스트도 깨진다.

세 근거 중 둘은 이번 작업으로 해소된다. "`less`가 접어서 같은 결과가 된다"는
`layout()`으로 접으면 제목 스타일이 모든 줄에 실리므로 더 이상 같은 결과가 아니고,
"폭 회귀 테스트가 깨진다"는 `layout()`이 폭 안에서 접으므로 발생하지 않는다.
남는 하나 — **접힌 제목이 본문과 구분되는가** — 에 4절이 답해야 한다.

### 무너지는 요소와 그 공통 원인

`less`는 소프트 랩(창 폭에서 접기)을 할 때 SGR 속성을 **유지한다.** 그래서 색은
접혀도 살아남는다. 반면 **줄머리에 찍은 것**은 이어지는 줄에 다시 찍히지 않는다.
무너지는 요소 셋이 정확히 여기서 갈린다.

| 요소 | 줄머리 의존 | 접히면 |
|---|---|---|
| 코드 펜스 `│ ` 거터 + `┌─ sql ─` / `└──` | 거터 글리프 | 이어지는 줄에 거터 없음 → 블록 밖처럼 보임 |
| 표 | 공백 패딩 정렬 | 열이 전부 어긋남 |
| `---`/`***` 수평선 | 폭을 정확히 채움 | 두 줄로 접힘 |

`_emit_fence`의 현재 주석은 이 트레이드오프를 이미 알고 강제 개행을 택했다고
기록한다("자르지 않으면 `less`가 접으면서 거터가 무너진다"). 목표가 바뀌었으므로
그 선택을 다시 연다.

## 목표

**접기 안전 불변식: 렌더 출력의 어떤 줄도 줄머리 위치에 의미를 싣지 않는다.**

`less`가 임의의 폭에서 접어도 (a) 정보가 소실되지 않고 (b) 어떤 줄이 무엇에
속하는지 알 수 있다. 이 불변식 하나가 네 증상 — 리사이즈, 좁은 폭, 표준 폭 표
압축, 제목 소실 — 을 전부 덮는다.

렌더 폭(`tui.text_width()`)은 여전히 **권장 폭**으로 남는다. 그 폭에서 가장
보기 좋고, 그 폭을 벗어나도 안 깨지는 것이 목표다.

## 비목표 (YAGNI)

- **실시간 재배치(SIGWINCH → `less` 재시작).** 파이프 입력이라 재시작하면 읽던
  위치를 잃고, 임시 파일 + `+<줄번호>`로 근사 복원해도 화면이 깜빡이며 위치가
  정확히 돌아오지 않는다. 리사이즈는 "접혀도 안 깨진다"로 대응한다.
- **모호폭(East Asian Ambiguous) 터미널 대응.** 렌더러가 쓰는 글리프
  (`─ │ ┌ └ ━ • · ◆`)는 전부 Ambiguous이고, ambiguous=2로 설정된 터미널에서는
  80칸 기준 853줄이 폭을 넘는다(실측, `CLAUDE.md`의 기록과 일치). `tui.cwidth`가
  이 가정을 저장소 전체에서 공유하고 터미널 설정을 감지할 이식 가능한 방법이 없다.
  `CLAUDE.md`가 확정 서술한 알려진 한계로 그대로 둔다.
- **벤더 열 좁히기.** 읽기 화면에서 고른 DBMS의 열만 남겨 4열 표를 2열로 줄이면
  치트시트가 카드형으로 떨어지는 것을 막을 수 있지만, `CLAUDE.md`의 "비교표는
  모든 브랜치에서 필터를 통과시킨다"는 원칙에 예외를 만들어야 한다. 별건으로 둔다.
- `tui.text_width()` / `page_text()` / `pager_supports_color()` 변경.
- `exam` / `shoot`의 화면 변경. 이 작업은 읽기 모드에만 닿는다.

## 1. 변경 범위

**`scripts/markdown_render.py` 단독.** `tui.py`와 `reading.py`는 손대지 않는다.
`text_width()`의 하한 40 / 상한 100도 그대로다.

렌더 3층(`inline_spans` → `layout` → `paint`)과 그 순서 계약은 유지된다. 바뀌는
것은 블록 방출 함수 셋(`_emit_fence`, `_emit_table`, `_emit_heading`)과
`render()`의 수평선 분기 하나뿐이다.

## 2. 코드 펜스 — 거터·테두리 폐지

`_emit_fence`

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 여는 줄 | `┌─ sql ` + 폭을 채우는 `─` | `sql` (dim). 언어 태그가 없으면 이 줄을 생략 |
| 본문 | `│ ` 거터 + `fit(body, width - 2)` 강제 개행 | `    `(4칸) + `fence` 스타일, **원문 그대로. 자르지도 접지도 않는다** |
| 닫는 줄 | `└` + 폭을 채우는 `─` | 제거. 뒤에 빈 줄 |

접혀서 무너질 거터가 사라진다. 부수 효과가 크다 — 지금은 강제 개행이 **원문
코드를 훼손**해 복사가 안 되는데(80칸 6%, 60칸 25%, 40칸 49%), 그게 같이 없어진다.

**들여쓰기를 4칸으로 두는 이유.** 챕터의 리스트 들여쓰기는 2·3칸 대역이라 겹치지
않고, 마크다운의 indented code block 관습과 맞는다.

**비용.** 무색 페이저(`PAGER=more`, `NO_COLOR=1`)에서 블록 경계 표시가 라벨 줄과
들여쓰기만 남는다. 지금은 `│`가 확실했다. 색과 구조를 분리한다는 기존 원칙에서
한 발 물러서는 유일한 지점이며, 접기 안전과 코드 복사 가능성을 얻는 대가로 받는다.

언어 태그 없는 펜스에서 여는 줄을 생략하면 이 비용이 커지지만, 실측상 저장소의
펜스 **259개 전부가 언어 태그를 가지고 있다**(sql 126, bash 92, ini 13, text 10,
yaml 7, markdown 5, hcl 5, conf 1). 태그 없는 경로는 현재 챕터에서 도달 불가이며,
새 챕터를 위한 방어 코드로만 남는다. 뜻 없는 라벨 줄을 지어내는 쪽이 더 나쁘다.

## 3. 표 — 안 들어가면 카드형

`_emit_table`

- **자연폭 ≤ width**: 지금 그대로 정렬 표. (실측 80칸에서 8/44가 여기 해당)
- **자연폭 > width**: 카드형으로 전환한다.

```
▸ 기본 포트
  PostgreSQL: 5432
  MySQL: 3306
  Oracle: 1521

▸ 접속 (`$`)
  PostgreSQL: `psql -h localhost -p 5432 -U postgres -d dbname`
  MySQL: `mysql -h localhost -P 3306 -u root -p`
  Oracle: `sqlplus system/pw@localhost:1521/XEPDB1`
```

첫 열이 카드 제목이 되고, 나머지 열은 `헤더: 값` 줄이 된다. 값이 길어 접히면
둘째 줄이 왼쪽 끝으로 가지만, `헤더:` 로 시작하는 줄이 항목 시작임을 알려주므로
줄머리 위치에 의존하지 않는다.

**카드 제목 표지는 `▸`를 쓴다.** `◆`(h2)와 `·`(h3)는 이미 제목 단계가 쓰고 있어,
재사용하면 표 카드가 챕터 제목으로 오독된다. 카드 제목과 `헤더:` 부분은 정렬 표의
헤더와 같은 `th` 스타일을 쓴다. 값 안의 인라인 마크업은 지금처럼 `inline_spans`를
통과한다.

전환 판정은 **자연폭 초과 여부 하나뿐이다.** 별도 임계 상수를 두지 않는다 —
"정렬 표를 그릴 수 있으면 그리고, 못 그리면 카드"가 규칙이다.

### 이 판정이 죽이는 코드

전환 기준이 자연폭 초과이므로 **정렬 표 경로에서 압축은 영영 일어나지 않는다.**
`_fit_columns`와 `_MIN_COL`은 압축 전용이었으므로 **삭제한다.** 열 폭은 이제
자연폭 그대로다.

| 심볼 | 처리 |
|---|---|
| `_fit_columns` | 삭제 — 압축이 사라지면 호출부가 없다 |
| `_MIN_COL` | 삭제 — `_fit_columns` 전용 상수였다 |
| `_pad` | 유지 — 정렬 표에서 셀을 자연폭에 맞춰 채운다 |
| `_alignments` | 유지 — 정렬 표에만 적용. 카드형에는 열 폭 개념이 없어 정렬 지시자가 의미를 갖지 않는다 |

정렬 표 경로에서 `layout(row[j], cols[j])`도 접을 일이 없어지지만(자연폭 = 최장 셀
폭), 셀 안 개행을 다루는 유일한 통로이므로 호출은 남긴다.

**대가.** 80칸에서 36/44가 카드형이 된다. 치트시트와 부록 비교 매트릭스의
"한 화면 비교" 성격은 넓은 터미널(자연폭 130칸 이상을 담을 수 있는 폭)에서만
유지된다. 벤더 열 좁히기(비목표 참조)가 이 대가를 줄이는 별건 후속 작업이다.

## 4. 제목 — 자르지 말고 접는다

`_emit_heading`의 `fit(text, width)`를 `layout()`으로 바꾼다. **제목 스타일
(`h1`/`h2`/`h3`)은 접힌 모든 줄에 실린다** — 이것이 배경에서 남겨 둔 근거,
"접힌 제목은 본문과 구분이 안 된다"에 대한 답이다. 굵게(+청록)가 둘째 줄에도
붙으므로 본문 문단과 구분된다.

무색 페이저에서는 이 구분이 약해진다. 다만 그 경우에도 **잘려서 사라지는 것보다는
낫다**: 제목 322개의 최대 폭이 73칸이고 권장 폭 하한이 40칸이므로, 접힘이 일어나는
구간은 정확히 지금 잘림이 일어나던 구간이다. 무색 + 좁은 폭에서 "구분이 약한 두 줄"과
"조용히 사라진 꼬리" 중 후자가 더 나쁘다.

h1은 위아래에 별도 막대 줄을 두지 않고 `━━━ 제목 ━━━`처럼 **같은 줄 안에** 막대를
넣는다. 제목이 두 줄이 되면 여는 `━━━`은 첫 줄 앞에, 닫는 `━━━`은 마지막 줄 뒤에
붙인다. 접두 장식 `◆`/`·`도 첫 줄에만 붙고, 둘째 줄부터는 왼쪽 끝에서 시작한다.

## 5. 구분선 — 폭 채우기 폐지

`render()`의 `---`/`***` 분기: `"─" * width` → `"─" * min(width, 24)`.
폭을 채우는 장식은 저장소에서 여기 한 곳뿐이다 — h1의 막대는 제목 줄 안에 있는
고정 3칸이라 폭에 의존하지 않는다.

24칸은 가장 좁은 지원 폭(`text_width()` 하한 40)에서도 여유롭게 들어가고, 구분선
구실을 하기에 충분한 길이다.

정렬 표의 헤더 아래 `─` 구분선은 **열 폭만큼 그리는 지금 방식을 유지한다.** 정렬
표는 자연폭이 들어갈 때만 그려지므로 접히지 않는다. 이 예외 때문에 6절의 장식줄
테스트는 표 헤더 구분선을 검사 대상에서 뺀다.

## 6. 검증

### `tests/test_markdown_render.py` — 신규 `ReflowSafetyTest`

저장소 챕터 전량을 픽스처로 쓰는 속성 테스트다. 이 파일은 이미 480줄이고
`BulletWidthPropertyTest`가 같은 방식의 전례를 만들어 두었다.

1. **코드 원문 보존** — 챕터 전량, 코드 펜스 원문의 각 줄이 렌더 출력에 통째로
   등장한다. 강제 개행 부재의 직접 검증이다.
2. **수평선 폭 비의존** — `---`/`***`에서 나온 구분선이 폭 40 / 78 / 120에서 모두
   같은 길이(24칸)다. **정렬 표의 헤더 구분선은 대상에서 뺀다**(5절의 예외) —
   표만 있는 픽스처와 수평선만 있는 픽스처를 나눠 이 경계를 명확히 한다.
3. **제목 무손실** — 폭 24~120 스윕, 모든 제목 텍스트가 출력에 남아 있다.
4. **접힌 제목이 제목 스타일을 유지한다** — 폭을 넘는 제목을 `color=True`로 렌더해
   둘째 줄에도 `h1`/`h2`/`h3` SGR이 붙는지 확인한다. 4절이 배경의 반론에 준 답을
   테스트로 고정하는 것이다.
5. **표 카드형 전환** — 자연폭 초과 픽스처에서 출력에 패딩 정렬이 없고 `헤더: 값`
   줄이 존재한다. 자연폭이 들어가는 픽스처에서는 정렬 표가 그대로 나온다.
6. **폭 보장 유지** — 코드 펜스 본문을 **제외한** 모든 줄이 `cwidth ≤ width`.

### 갱신되는 기존 테스트

계약이 바뀌므로 다음은 의도적으로 고쳐 쓴다. 삭제가 아니라 새 계약으로 다시
쓰는 것이며, 각각 무엇을 지키던 테스트였는지 새 이름에 남긴다.

| 테스트 | 바뀌는 이유 |
|---|---|
| `test_a_fence_gets_a_box_with_the_language_label` | 테두리 상자가 없어진다 → 라벨 줄 + 들여쓰기 검증으로 |
| `test_a_fence_without_a_language_still_gets_a_box` | 언어 태그 없으면 라벨 줄도 없다 → 들여쓰기만 검증 |
| `test_a_long_code_line_is_split_not_lost` | 이제 쪼개지도 않는다 → "원문 그대로 나온다"로 |
| `test_the_box_never_exceeds_the_width` | 코드 줄은 이제 폭을 넘을 수 있다 → 폭 보장 예외를 명시하는 테스트로 |
| `test_long_ascii_language_tag_does_not_overflow` | 라벨 줄은 `fit`으로 폭 안에 유지 → 검증 대상만 축소 |
| `test_long_korean_language_tag_does_not_overflow` | 위와 같다 |
| `test_a_horizontal_rule_spans_the_width` | 폭을 채우지 않는다 → `min(width, 24)` 검증으로 |
| `TableTest.test_a_wide_table_wraps_inside_its_cells` | 넓은 표는 이제 셀 안에서 접히지 않고 카드형이 된다 → 카드형 검증으로 |
| `TableTest.test_a_wrapped_cell_keeps_its_column_start` | 위와 같다. 셀 접힘 자체가 사라진다 |
| `TableTest.test_a_wrapped_cell_pads_each_continuation_line_by_its_alignment` | 위와 같다 |
| `RealChapterTest.test_no_rendered_line_exceeds_the_width` | **코드 펜스 본문 예외가 생긴다.** 이 저장소에서 새 계약을 가장 정면으로 마주하는 테스트다 → 펜스 본문을 제외한 나머지에 대해 같은 보장을 건다 |

`TableTest`의 정렬 관련 테스트(`test_right_alignment_pads_before_the_value`,
`test_centre_alignment_pads_both_sides`)는 픽스처가 좁은 표라 정렬 표 경로로 남으므로
그대로 통과해야 한다. 깨진다면 카드형 전환 판정이 자연폭보다 공격적으로 걸린 것이다.

`test_a_heading_is_preceded_by_a_blank_line` 등 제목 관련 기존 테스트는 짧은
제목에 대해 동작이 같으므로 그대로 통과해야 한다. 통과하지 않는다면 4절 변경이
의도보다 넓게 퍼진 것이다.

### CI

표준 라이브러리만 쓰고 새 워크플로도 없다. `python3 -m unittest discover -s tests`
그대로다.

### 실행 검증

전체 테스트 통과 후 `./guide` → 챕터 읽기로 눈으로 확인한다.

- `01-beginner/07-commands-cheatsheet.md` — 4열 표의 카드형 전환
- `appendix/dbms-comparison-matrix.md` — 가장 넓은 표(192칸)
- `03-advanced/` 중 코드 펜스가 긴 챕터 — 들여쓰기 코드 블록과 복사 가능성
- 읽는 중 터미널 폭을 절반으로 줄여 접힘 확인 (이번 작업의 핵심 목표)
- `PAGER=more ./guide`, `NO_COLOR=1 ./guide` — 무색 경로에서 (a) 코드 블록 경계가
  라벨 줄 + 들여쓰기로 식별되는지, (b) 좁은 폭에서 접힌 긴 제목이 본문으로 오독되지
  않는지. 4절이 받아들인 트레이드오프가 실제로 견딜 만한지 보는 항목이다

### 문서

  접으면서 거터가 무너진다")을 새 결정으로 바꿔 쓴다. 왜 거터를 버렸는지가
  다음 사람에게 남아야 한다.

  본문이라는 예외가 생겼다**는 점 — 지금 문서는 예외 없는 보장으로 읽힌다.
  모호폭 한계 서술은 그대로 둔다.
