# 01. 관계형 데이터베이스 기초

## 1. 핵심 개념 설명

**데이터베이스(Database)** 는 여러 사람이 함께 쓰는 데이터를 체계적으로 모아 둔 저장소입니다. 그리고 이 데이터를 관리해 주는 소프트웨어를 **DBMS(Database Management System)** 라고 부릅니다. 그중에서도 데이터를 **표(table) 형태**로 저장하고, 표들 사이의 **관계(relationship)** 로 데이터를 연결하는 방식이 **관계형 데이터베이스(RDBMS, Relational DBMS)** 입니다. PostgreSQL, MySQL, Oracle이 모두 여기에 속합니다.

관계형 모델이 오랫동안 사랑받는 이유는 **단순하면서도 강력하기 때문**입니다. 사람은 표를 보면 직관적으로 이해합니다. "직원" 표에는 직원 정보가 한 줄씩 들어 있고, "부서" 표에는 부서 정보가 들어 있으며, 직원 표의 `부서번호` 열이 부서 표를 가리키는 식입니다. 이렇게 데이터를 잘게 나누어 저장하면 **중복을 줄이고, 데이터가 서로 모순되는 것을 막을 수 있습니다.** 예를 들어 부서 이름이 바뀌어도 부서 표 한 곳만 고치면 됩니다.

실무에서 DBA는 이 관계형 모델의 규칙을 이해하고 있어야 합니다. 테이블을 어떻게 나눌지(정규화), 데이터가 깨지지 않도록 어떤 제약(제약조건)을 걸지, 여러 작업이 동시에 일어날 때 데이터를 어떻게 안전하게 지킬지(ACID)를 판단하는 것이 DBA의 기본 업무이기 때문입니다.

### 관계형 모델의 구성 요소

| 용어 | 다른 이름 | 설명 |
|------|-----------|------|
| 테이블(Table) | 릴레이션(Relation) | 데이터를 담는 표 자체. 예: `employees` |
| 행(Row) | 레코드(Record), 튜플(Tuple) | 표의 한 줄. 하나의 데이터 항목. 예: "홍길동, 개발팀" |
| 열(Column) | 필드(Field), 속성(Attribute) | 표의 세로 항목. 예: `name`, `department_id` |
| 관계(Relationship) | — | 테이블과 테이블을 연결하는 논리적 연결. 주로 외래키로 표현 |

### ACID — 트랜잭션의 4가지 보장

**트랜잭션(Transaction)** 은 "함께 성공하거나 함께 실패해야 하는 하나의 작업 묶음"입니다. 대표적인 예가 계좌 이체입니다. "A 계좌에서 1만 원 빼기"와 "B 계좌에 1만 원 넣기"는 반드시 둘 다 되거나 둘 다 안 되어야 합니다. 이런 안전성을 보장하는 4가지 성질이 ACID입니다.

- **A (Atomicity, 원자성)**: 트랜잭션 안의 작업들은 전부 반영되거나 전부 취소된다. 중간까지만 반영되는 일은 없다.
- **C (Consistency, 일관성)**: 트랜잭션이 끝나면 데이터는 항상 정해진 규칙(제약조건)을 만족하는 상태여야 한다.
- **I (Isolation, 격리성)**: 여러 트랜잭션이 동시에 실행되어도 서로 간섭하지 않고, 마치 하나씩 순서대로 실행된 것처럼 보인다.
- **D (Durability, 지속성)**: 한 번 완료(COMMIT)된 데이터는 정전이 나도 사라지지 않고 영구히 저장된다.

### 정규화(Normalization) — 1NF부터 3NF까지

**정규화**는 데이터 중복과 이상 현상(데이터가 꼬이는 문제)을 줄이기 위해 테이블을 잘 나누는 규칙입니다. 단계별로 지켜야 할 조건이 있습니다.

- **1NF (제1정규형)**: 모든 칸(열)에는 값이 **하나만** 들어가야 한다. 예를 들어 `전화번호` 칸에 "010-1111, 010-2222"처럼 여러 값을 넣으면 안 된다.
- **2NF (제2정규형)**: 1NF를 만족하면서, 기본키가 여러 열로 이루어진 경우 **기본키 전체에 완전히 의존**하는 열만 남긴다. 기본키의 일부에만 딸린 정보는 다른 테이블로 뺀다.
- **3NF (제3정규형)**: 2NF를 만족하면서, 기본키가 아닌 열이 **다른 일반 열에 의존하면 안 된다.** 예: 직원 테이블에 `부서번호`와 `부서이름`이 함께 있으면, `부서이름`은 `부서번호`에 딸린 정보이므로 부서 테이블로 분리한다.

정규화를 잘하면 데이터 수정이 쉬워지지만, 테이블이 너무 잘게 쪼개져 조회 시 JOIN이 많아질 수 있습니다. 이 균형을 잡는 것은 중급 이후의 주제입니다. 초급에서는 "중복을 줄이려고 테이블을 나눈다"는 감각을 익히면 충분합니다.

## 2. 주요 개념/문법

관계형 모델의 규칙은 대부분 **제약조건(Constraint)** 으로 데이터베이스에 강제합니다. 세 DBMS의 문법은 표준 SQL을 따르므로 거의 동일합니다.

### 기본키(Primary Key)와 외래키(Foreign Key)

- **기본키**: 각 행을 유일하게 구분하는 열. 중복 불가, NULL 불가. 예: 직원의 `id`.
- **외래키**: 다른 테이블의 기본키를 가리키는 열. 테이블 간 관계를 만든다. 예: 직원의 `department_id`가 부서 테이블의 `id`를 참조.

**PostgreSQL / MySQL / Oracle 공통 문법**

```sql
-- 부서 테이블 (부모)
CREATE TABLE departments (
    id   INT PRIMARY KEY,        -- 기본키
    name VARCHAR(50) NOT NULL    -- 부서명은 반드시 값이 있어야 함
);

-- 직원 테이블 (자식)
CREATE TABLE employees (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(id)  -- 외래키
);
```

> **DBMS별 차이**: 자동 증가 기본키 문법은 DBMS마다 다릅니다.
>
<!-- dbms:postgresql -->
> - PostgreSQL: `SERIAL` 또는 `GENERATED ALWAYS AS IDENTITY`
<!-- /dbms:postgresql -->
<!-- dbms:mysql -->
> - MySQL: `AUTO_INCREMENT`
<!-- /dbms:mysql -->
<!-- dbms:oracle -->
> - Oracle: `GENERATED BY DEFAULT AS IDENTITY`(12c 이상)
<!-- /dbms:oracle -->
>
> 자세한 정수·자동증가 타입은 02장에서 다룹니다.

### 주요 제약조건

```sql
CREATE TABLE members (
    id       INT PRIMARY KEY,                       -- 기본키
    email    VARCHAR(100) UNIQUE,                   -- 중복 불가 (유일값)
    name     VARCHAR(50) NOT NULL,                  -- NULL 불가 (필수 입력)
    age      INT CHECK (age >= 0),                  -- 조건 검사 (0 이상만 허용)
    country  VARCHAR(2) DEFAULT 'KR'                -- 기본값 지정
);
```

- **NOT NULL**: 빈 값(NULL)을 허용하지 않음. 반드시 값이 있어야 하는 열에 사용.
- **UNIQUE**: 값이 서로 중복되지 않도록 보장. 예: 이메일, 주민번호.
- **CHECK**: 값이 특정 조건을 만족하는지 검사. 예: 나이는 0 이상.
- **DEFAULT**: 값을 넣지 않으면 자동으로 채워지는 기본값.

## 3. 실습 예제

**시나리오: 부서와 직원을 표현하는 두 테이블을 만들고, 관계가 어떻게 강제되는지 확인해 보자.**

```sql
-- 1) 부서 테이블 생성
CREATE TABLE departments (
    id   INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);

-- 2) 직원 테이블 생성 (부서를 외래키로 참조)
CREATE TABLE employees (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(id)
);

-- 3) 부서 데이터 먼저 입력 (부모가 있어야 자식이 참조 가능)
INSERT INTO departments (id, name) VALUES (1, '개발팀');
INSERT INTO departments (id, name) VALUES (2, '인사팀');

-- 4) 직원 데이터 입력 (존재하는 부서만 참조 가능)
INSERT INTO employees (id, name, department_id) VALUES (101, '홍길동', 1);
INSERT INTO employees (id, name, department_id) VALUES (102, '김영희', 2);

-- 5) 존재하지 않는 부서(99)를 참조하면? → 외래키 위반으로 오류 발생!
INSERT INTO employees (id, name, department_id) VALUES (103, '이철수', 99);
--   ERROR: 외래키 제약조건 위반 (부서 99가 없음)

-- 6) 확인: 직원과 부서를 함께 조회
SELECT e.name AS 직원, d.name AS 부서
FROM employees e
JOIN departments d ON e.department_id = d.id;
```

5번에서 오류가 나는 것이 바로 관계형 모델의 힘입니다. 데이터베이스가 스스로 "없는 부서에 직원을 넣을 수 없다"는 규칙을 지켜 줍니다. DBA는 이런 제약을 설계하고 관리합니다.

## 4. 체크리스트

- [ ] 테이블, 행, 열, 관계가 각각 무엇인지 예를 들어 설명할 수 있다.
- [ ] ACID의 네 글자(원자성·일관성·격리성·지속성)가 무슨 뜻인지 말할 수 있다.
- [ ] 트랜잭션이 "함께 성공하거나 함께 실패하는 작업 묶음"임을 이해했다.
- [ ] 1NF, 2NF, 3NF의 조건을 각각 한 문장으로 설명할 수 있다.
- [ ] 주어진 테이블을 보고 정규화 위반(예: 한 칸에 여러 값)을 찾아낼 수 있다.
- [ ] 기본키와 외래키의 차이, 외래키가 관계를 만드는 원리를 설명할 수 있다.
- [ ] NOT NULL, UNIQUE, CHECK, DEFAULT 제약조건의 역할을 구분할 수 있다.
- [ ] 외래키가 걸린 테이블에서 없는 부모를 참조하면 오류가 나는 이유를 안다.
