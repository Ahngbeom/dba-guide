# 04. 확장과 샤딩 (Scaling & Sharding)

## 1. 핵심 개념 설명

데이터베이스 확장은 "성능이 부족하다"는 증상에서 출발하지만, 해결책은 부하의 **성격**에 따라 완전히 달라진다. 읽기가 병목인가 쓰기가 병목인가, CPU인가 I/O인가 커넥션인가, 데이터 크기 자체가 문제인가를 먼저 진단하지 않고 샤딩부터 도입하면 복잡성만 폭증한다. 확장 전략은 **가장 단순한 것부터 순서대로** 검토하는 것이 원칙이다.

### 확장의 사다리 (단순 → 복잡)

1. **수직 확장(Scale-up)**: 인스턴스 스펙(CPU/RAM/IOPS) 상향. 가장 빠르고 애플리케이션 변경이 없다. 한계가 명확하고(하드웨어 상한) 비용이 가파르며, 단일 장애점을 키운다는 단점. **하지만 대부분의 서비스는 여기서 충분하다** — 성급한 분산화를 경계하라.
2. **읽기 확장(Read Replica)**: 읽기 트래픽을 여러 복제본으로 분산. 읽기 대 쓰기 비율이 높은(예: 9:1) 전형적 웹 서비스에 매우 효과적. 단, **복제 지연(replication lag)**으로 인한 "방금 쓴 걸 못 읽는" 문제를 애플리케이션이 다뤄야 한다.
3. **수평 확장/샤딩(Scale-out, Sharding)**: 데이터를 샤드 키 기준으로 여러 물리 노드에 나눠 저장. **쓰기까지 분산**되는 유일한 방법이지만, 조인·트랜잭션·유니크 제약이 샤드를 넘으면 매우 어려워진다. 진짜 최후의 수단.

### 리드 리플리카 활용의 실제
- **읽기/쓰기 분리(Read-Write Splitting)**: 쓰기는 Primary, 읽기는 리플리카로 라우팅. 드라이버·프록시(ProxySQL 등)·애플리케이션 레벨에서 구현.
- **복제 지연 대응**: "쓰기 직후 읽기"는 Primary로 보내거나(read-your-writes), 지연 임계값을 넘는 리플리카는 라우팅에서 제외.
- 리드 리플리카는 **읽기 부하 분산 + 리포팅/분석 오프로드 + DR 후보**의 1석 3조지만, 쓰기 병목은 절대 못 푼다.

### 샤딩 전략과 샤드 키 설계
샤딩의 성패는 **샤드 키 선택**에 90% 달려 있다.
- **해시 샤딩(Hash)**: 샤드 키를 해시해 균등 분산. 핫스팟은 적지만 범위 조회가 모든 샤드로 퍼진다(scatter-gather).
- **범위 샤딩(Range)**: 키 범위로 분할. 범위 조회에 유리하지만 최신 데이터에 쓰기가 몰리는 **핫스팟** 위험.
- **디렉터리/룩업 샤딩**: 키→샤드 매핑 테이블 유지. 유연하지만 매핑 계층이 단일 장애점·병목이 될 수 있다.
- **지역 기반(Geo)**: 사용자 위치로 분할. 데이터 주권 규제·지연 최적화에 유리.

좋은 샤드 키의 조건: ① 카디널리티가 높아 고르게 분산되고, ② 대부분의 쿼리가 그 키를 포함해 단일 샤드에서 처리되며(크로스 샤드 회피), ③ 시간이 지나도 재분배(resharding)가 드물어야 한다. 예: 멀티테넌트 SaaS는 `tenant_id`가, 소셜 서비스는 `user_id`가 흔한 선택이다. 반면 `created_at` 같은 순증 키는 핫스팟 때문에 나쁜 샤드 키다.

## 2. 주요 명령어/문법

### 리드 리플리카 생성

**PostgreSQL (스트리밍 리플리카)** — 02장과 동일 메커니즘, 읽기 오프로드 용도
```ini
# 리플리카에서 읽기 허용 (기본으로 hot standby)
hot_standby = on
# Primary: 리플리카 지연 모니터링
```
```sql
-- Primary에서 리플리카 지연(바이트) 확인
SELECT client_addr, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;
```


**클라우드**
```bash
aws rds create-db-instance-read-replica --db-instance-identifier proddb-ro-1 \
  --source-db-instance-identifier proddb
gcloud sql instances create proddb-ro-1 --master-instance-name=proddb --region=asia-northeast3
```

### 애플리케이션 레벨 커넥션 풀링 / 라우팅

**PgBouncer (PostgreSQL, 커넥션 풀)**
```ini
[pgbouncer]
pool_mode = transaction
max_client_conn = 10000
default_pool_size = 50
```


### 샤딩 (개념적 예시)
```text
샤드 라우팅 (애플리케이션/미들웨어):
  shard_id = hash(tenant_id) % SHARD_COUNT
  → shard_id 로 해당 DB 커넥션 풀 선택 후 쿼리 실행
```

```text
Postgres 계열 확장:
  - Citus: 분산 테이블 (SELECT create_distributed_table('events','tenant_id'))
```

## 3. 실습 예제

**시나리오: "멀티테넌트 SaaS. Primary 단일 노드가 쓰기 CPU 90%, 데이터 4TB. 어떻게 확장하나?"**

1. **진단 먼저**: 병목이 읽기인지 쓰기인지 계측. 읽기가 70%면 → 리드 리플리카부터. 쓰기 자체가 한계면 → 샤딩 검토.

2. **1단계 — 수직 확장으로 시간 벌기**: 인스턴스를 상위 스펙으로 올려 급한 불을 끈다. 애플리케이션 무변경. 이 시간에 다음 단계를 설계한다.

3. **2단계 — 읽기 오프로드**: 리드 리플리카 2대 추가, ProxySQL/드라이버로 읽기 라우팅. 리포팅·대시보드 쿼리는 전용 리플리카로 분리. 복제 지연 임계값(예: 5초) 초과 리플리카는 자동 제외.

4. **3단계 — 샤딩 설계(쓰기가 여전히 병목일 때)**:
   - **샤드 키**: `tenant_id` 선택. 대부분의 쿼리가 특정 테넌트 범위이고(단일 샤드 처리), 테넌트별 데이터가 격리되어 크로스 샤드 조인이 드물다.
   - **분산 방식**: 해시 샤딩으로 4개 샤드에 균등 분산. 단, 초대형 테넌트가 한 샤드를 독식하는 것을 막기 위해 **대형 테넌트는 전용 샤드**로 분리하는 하이브리드(디렉터리 매핑) 적용.
   - **크로스 샤드 문제 처리**: 전체 집계는 각 샤드에서 부분 집계 후 애플리케이션에서 병합(scatter-gather). 샤드 간 트랜잭션이 필요한 기능은 설계 단계에서 제거하거나 Saga 패턴으로 대체.
   - **리샤딩 대비**: 처음부터 논리 샤드(예: 1024개)를 물리 노드에 매핑해두면, 노드 증설 시 논리 샤드만 옮기면 되어 재분배가 수월하다.

5. **검증**: 샤딩 도입 전후로 쓰기 TPS, p99 지연, 노드별 부하 균형을 계측. 핫샤드가 생기면 샤드 키/매핑을 재검토.

> **트레이드오프 메모**: 샤딩은 되돌리기 매우 어려운 결정이다. 도입 순간부터 애플리케이션은 "샤드를 아는" 코드가 되고, 스키마 변경·백업·모니터링·조인이 전부 복잡해진다. **"수직 확장 + 리드 리플리카로 정말 안 되는가?"를 세 번 자문한 뒤**, 그래도 쓰기 확장이 필요할 때만 샤딩하라. 또는 분산 SQL(Citus/Vitess/CockroachDB/Spanner)로 이 복잡성을 데이터베이스에 위임하는 선택지도 검토할 가치가 있다.

## 4. 체크리스트

- [ ] 확장 문제를 만났을 때 읽기/쓰기·CPU/IO/커넥션 중 무엇이 병목인지 먼저 진단한다.
- [ ] 수직 확장 → 리드 리플리카 → 샤딩의 순서로 단순한 해법부터 검토한다.
- [ ] 리드 리플리카로 읽기/쓰기를 분리하고 복제 지연 문제를 애플리케이션에서 처리할 수 있다.
- [ ] 해시/범위/디렉터리/지역 샤딩의 트레이드오프를 설명할 수 있다.
- [ ] 좋은 샤드 키의 3가지 조건(고른 분산·단일 샤드 처리·낮은 리샤딩 빈도)으로 키를 평가할 수 있다.
- [ ] 크로스 샤드 조인·트랜잭션·집계의 어려움과 대안(scatter-gather, Saga)을 안다.
- [ ] PgBouncer로 커넥션 풀링을 구성할 수 있다.
- [ ] 샤딩 도입 전 "정말 필요한가"를 비용·복잡성 관점에서 판단할 수 있다.
