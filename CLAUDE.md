# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a Korean-language learning guide for becoming a Database Administrator (DBA). It is overwhelmingly Markdown content organized into a three-tier curriculum: `01-beginner` → `02-intermediate` → `03-advanced`, plus an `appendix/`. "Development" here mostly means writing and editing Markdown chapters.

The only executable code is a small set of **standard-library-only Python3 / Bash tools in `scripts/`** — no `pip`/`npm`/build system, no CI. Keep it that way: any new tooling must use only the Python standard library (no external packages). Current tools:
- `install.sh` (repo root) — one-line installer: clones into `${XDG_DATA_HOME:-~/.local/share}/dba-guide`, checks out the **latest release tag** (never `main` HEAD — there is no CI here, so only tagged commits have been hand-checked), and symlinks `guide`/`exam`/`shoot` into `~/.local/bin`. Same script handles update (re-run, idempotent) and removal (`--uninstall`, plus `--purge` to delete the tree). Three rules it must never break: (1) it refuses to touch anything it did not create — a foreign file at a launcher name, a non-git directory at the install path, and tracked local modifications each stop the run; (2) `--uninstall` keeps the directory, because `.exam-results/` and `.shooting-progress/notes/` are gitignored and have no other copy; (3) run from inside a clone it links in place and **never moves HEAD**, so a contributor's branch does not get detached onto a tag. Must stay **bash 3.2 compatible** — macOS ships 3.2.57 and `curl | bash` uses it. Because it links the launchers, **`guide`/`exam`/`shoot` must each resolve their own symlink chain** before deriving `$here` — `${BASH_SOURCE[0]}` is the link's own path, not its target, so the naive `dirname` sends them looking for `~/.local/bin/scripts/*.py`. That shipped broken in v1.2.0 and was fixed in v1.2.1; `readlink -f` is not portable, hence the hand-rolled loop. Tests: `tests/test_install.py` runs the real script against a `file://` origin, copying it to a temp dir first (running the in-repo copy would make `BASH_SOURCE` trigger in-place mode and void every managed-mode test). Its fixture copies the **real** launchers rather than stubbing them, and `LinkedCommandTest` **executes the installed command through its symlink** — asserting `os.readlink` alone is what let v1.2.0 ship with all three commands broken.
- `scripts/generate-branch.sh` + `scripts/filter_dbms.py` — single-vendor branch generation (see below).
- `guide` (repo-root launcher) + `scripts/guide.py` — top-level menu that offers the three runners below and hands off to them. It only wraps: picking a mode drops out of curses and calls `exam.main([])`, `shooting.main([])`, or `reading.main([])`, then returns to the menu. It must catch `SystemExit` (exam.main raises it wherever it gives up, and reading.main propagates it unchanged from its own chapter→exam handoff) and `KeyboardInterrupt` (shooting.main does not catch its own) — otherwise finishing one mode kills the launcher. Run `./guide` with no arguments; `./exam` and `./shoot` remain the way to pass flags. The third mode is `scripts/reading.py`: DBMS → tier → chapter, body handed to `$PAGER`, then an offer to run that chapter's bank. Vendor filtering calls `filter_dbms.filter_lines`, the same function `generate-branch.sh` uses, so the in-place view and the single-vendor branches cannot drift.
- `exam` (repo-root launcher) + `scripts/exam.py` — TUI learning-check quiz/exam runner (curses, line-mode fallback). Run `./exam` with no args to pick DBMS → tier → chapter interactively in the TUI; CLI args (a bank path/tier, `--dbms`, `--shuffle`) still work and skip the matching selection screen. `scripts/seed_exam.py` — generates draft question banks from a chapter. Question banks live in `exams/<tier>/<chapter>.json`. Tests: `python3 -m unittest discover -s tests`. Full convention: `docs/exam-authoring.md`. When adding or substantially changing a chapter, update (or regenerate + refine) the matching `exams/**/*.json` so the quiz stays in sync; keep chapter-specific commands as `short` questions tagged with the right `dbms`. `exam_bank_for(chapter_rel)` maps a chapter path to its bank (`exams/<tier>/<name>.json`, None when there is none) and lives here because both the shooting clear screen and the chapter reader need the same mapping.
- `shoot` (repo-root launcher) + `scripts/shooting.py` — incident-response game runner. Injects real faults into a local Docker MySQL lab (`shooting/lab/compose.yaml`, containers `dbshoot-primary`/`dbshoot-replica`) and judges the player's recovery. Stages are declarative JSON in `shooting/stages/*.json`. Subcommands: `./shoot doctor | up | down | notes | --list`. Full convention: `docs/shooting-game.md`. Things to know before touching it: (1) judging rests on **user separation** — `dba` is the player (watched via `mysql.general_log`), `app` is engine-spawned fault sessions, `repl` is the replication account, `root@localhost` is the engine itself; (2) engine-spawned sessions **must** pass `mysql --no-defaults`, because the container's `/root/.my.cnf` outranks `MYSQL_PWD` and would silently break auth; (3) `state` objectives need `hold_seconds` or a transient blip clears the stage; (4) the command log is **per server** — it is read on every watched container, and `KILL` targets/culprit pids are `(target, pid)` pairs because pids collide across servers; (5) the engine's own log-truncation **must** carry `NO_BINLOG` (`SET SESSION sql_log_bin = 0`), or it replicates and wipes the replica's log mid-cycle, silently erasing everything the player did there — stage `sql` steps, by contrast, are meant to replicate; (6) load-generating stored procedures **must** be `SQL SECURITY INVOKER`, since a `DEFINER` procedure reports `processlist.user` as the definer (root) and makes `app` sessions invisible to session tracking and cleanup; (7) `DELIMITER` is line-oriented, so procedure-creating `sql` steps need real `\n` around it — and it must **not be the first thing** in the step, because the engine prepends `SET SESSION sql_log_off = 1; ` and would leave it mid-line (start such a step with `\n`); (8) the engine is **vendor-dispatched by `target`** — containers are vendor-specific (`primary`/`replica` → MySQL, `postgres` → PostgreSQL), so `db_query()`/`db_spawn()`/`read_player_commands()` branch internally and call sites never name a vendor; a stage sets `dbms` and `normalize_targets()` fills omitted `on`/`source` **once at load time** (resolving the default at each read site instead lets one missed `.get("on", "primary")` silently query the wrong server); (9) PostgreSQL judging has two holes MySQL doesn't — **parse errors never reach the watch source** (measured: semantic and permission errors do, `KILL 999999` doesn't) and `SELECT pg_terminate_backend(pid) FROM pg_stat_activity` sweeps without naming a pid, so `kill_precision` can't see it (use `forbidden_command`); (10) statements executed **inside a stored procedure never get their own row** in `events_statements_summary_by_digest` (only the outer `CALL` does), so a stage cannot use statement digests as its diagnostic path while load comes from a procedure — `SHOW PROCESSLIST` does show the inner statement; relatedly, what the load query *reads* decides the plan (a `COUNT(*)` answerable from the index yields a covering `type=index` scan, not the `key=NULL` fingerprint an implicit-conversion stage is teaching), so always run the screen the stage claims the player will see; (11) **never rebuild a terminal tool inside curses.** A hand-rolled SQL console (editor + pager + completion, 363 lines) was deleted after it proved worse than the real client on every axis and its keymap kept colliding with the game HUD. `run_in_terminal()` (`def_prog_mode` → `endwin` → subprocess → `reset_prog_mode`) is the one channel — the mysql client (`c`), `$EDITOR` for postmortem notes, and `$PAGER` for reading them all go through it. Judging is unaffected because it keys on the logged user, not the input path; (12) a `sessions` setup step can hand each spawned session `{{session_index}}` (0-based), but that name is usable **only inside that step's own `sql`** — validation rejects it anywhere else, because nowhere else does it get substituted, so the literal `{{session_index}}` would otherwise reach real SQL or the player's screen unrendered; and locking stages are **vendor-dispatched** on top of that — when several sessions target the same row, InnoDB queues waiters on one record-lock and reports the **lock holder** as blocker (so MySQL 1-3 can pile every victim onto the same row), but PostgreSQL serializes waiters on the same tuple via **tuple lock**, so `pg_blocking_pids` names a mid-chain waiter instead (measured: with 4 victims on one row, the culprit showed up in only one of the four blocked rows, and the last waiter's blockers didn't include the culprit at all) — so PostgreSQL locking stages must split victims by `{{session_index}}` onto distinct rows; (13) a stage's diagnostic mcq choices are **shuffled by that game's seed** — write the correct one at `answer: 0` per the `exam.py` authoring convention, and pin `shuffle: false` on any question where choice order itself carries meaning.
- Postmortem notes live in `.shooting-progress/notes/<stage-id>/<stamp>-<rank>.md` (gitignored). `build_note()` fills only **observed facts** (timeline from `session["events"]`, wrong quiz answers, violations) and deliberately leaves root cause / 5 Whys / action items blank — filling those in is the exercise. That is why the stage `debrief` never appears in the draft: `append_debrief()` adds it to the file only **after** the editor exits (idempotent, guarded by `DEBRIEF_MARKER`), so the player writes blind but the archived note still holds their analysis next to the official answer. Giving up deliberately does **not** attach the debrief — otherwise quitting becomes the shortcut to the answer.
- `scripts/tui.py` — curses primitives (display width, safe drawing, key normalization) **shared by `exam.py` and `shooting.py`**. It takes `curses` as a parameter rather than importing it, so the width/wrap functions stay unit-testable. Put new terminal-drawing helpers here rather than duplicating them in either runner. **Before writing a "pick one from a vertical list" screen, use `pick()`** — that shape had drifted into three separate implementations before it was consolidated here, each re-solving the key-comparison trap below on its own. **Key comparison trap:** `read_key(wide=False)` returns ints from `getch()` while `wide=True` returns strs from `get_wch()` — the same `q` is `113` in one mode and `"q"` in the other. Always compare through `key_char()`/`is_enter()`/`is_backspace()`; comparing raw values silently kills whichever representation you didn't handle. (`exam.py` predates these helpers and compares with `ord()`, which is correct — leave it alone.) `page_text()` (hand text to `$PAGER`) and `pick_line()` (the plain-text twin of `pick()`) live here too — `pick_line` was consolidated from three runner-local copies for the same reason `pick` was, and the chapter reader would have made a fourth. `tui.py` therefore touches `os`/`subprocess`, which the width and key helpers do not.

## Content architecture

- **Progression is encoded in directory names, not just content.** `01-beginner/`, `02-intermediate/`, `03-advanced/` map to career stages (예비/신입 DBA → 실무 독립 수행 DBA → 시니어 DBA/DB 아키텍트). Each tier's `00-overview.md` states prerequisites and a checklist for graduating to the next tier — read it before adding or reordering chapters in that tier.
- **Chapters are numbered and vendor-neutral by design.** The guide deliberately avoids committing to one DBMS; every chapter (except `00-overview.md`) covers a concept once and gives commands for PostgreSQL, then MySQL, then Oracle (MSSQL where relevant) in that fixed order, calling out divergence only when the behavior differs meaningfully — not just syntax.
- **Every chapter file (except `00-overview.md`) follows the same four-section structure**, in this order:
  1. `## 핵심 개념 설명` — why the concept matters, when it comes up in practice
  2. `## 주요 명령어/문법` — commands/syntax, PostgreSQL → MySQL → Oracle
  3. `## 실습 예제` — a short scenario-driven walkthrough
  4. `## 체크리스트` — `- [ ]` checkbox list of what the reader should now be able to do
  New chapters must follow this exact section order and heading names so the guide reads consistently across tiers.
- **`00-overview.md` in each tier uses a different structure**: prerequisites / competencies gained / criteria (checklist) for moving to the next tier (the top-level advanced overview instead describes ongoing growth directions, since there is no tier after it).
- **Each tier ends with a `*-commands-cheatsheet.md`** — a single-page Markdown table summarizing that tier's commands across the three DBMSes. When adding a command to a chapter, add the corresponding row to that tier's cheatsheet.
- **`appendix/dbms-comparison-matrix.md`** is the cross-tier, cross-DBMS reference table (including cloud managed services — AWS/GCP/Azure) and **`appendix/glossary.md`** is the cross-tier term glossary. These are meant to be kept in sync with terms/commands introduced in any tier's chapters — when introducing a new term or command in a chapter, consider whether it belongs in one or both of these appendix files too.
- **`README.md`** is the table of contents and learning roadmap; every chapter file is linked from it by relative path. Adding, removing, or renaming a chapter file requires updating the corresponding row/link in `README.md`.
- **Single-vendor branches (`postgresql`/`mysql`/`oracle`) are auto-generated from `main`.** `main` stays vendor-neutral; DBMS-specific paragraphs/code blocks/checklist items can be wrapped in `<!-- dbms:postgresql -->...<!-- /dbms:postgresql -->` (and `mysql`/`oracle`) markers, and `scripts/generate-branch.sh <dbms>` filters them into a single-vendor view of a chapter. Never hand-edit content directly on those branches — regenerate from `main` instead. Cheatsheets and the appendix comparison/glossary files are intentionally left unmarked (they're comparison tables by design) and pass through unfiltered on every branch. Full convention and the per-chapter marking-progress tracker live in `docs/dbms-branch-strategy.md`.

## Working in this repository

- All content is written in Korean; keep new content in Korean, consistent with the rest of the guide.
- Preserve the chapter filename convention: two-digit prefix + kebab-case topic (e.g., `04-user-and-privilege-management.md`). The prefix determines reading order within a tier.
- Cross-references between chapters use relative Markdown links (e.g., `03-advanced/03-disaster-recovery.md` linking to `07-cloud-managed-db-advanced.md`); keep links relative to the repository root or the linking file, matching existing usage.
- **Releases are tagged on `main` only, and always go out as a GitHub draft first.** A draft release does not create the tag ref, so it stays fully reversible until published; the vendor branches never get tags because they are regenerated from `main` and any tag on them would be orphaned by the next regeneration. Version bumps follow SemVer read as "does anything outside this repo break" — chapter/stage/question-bank additions are MINOR even in bulk, and MAJOR is reserved for incompatible JSON schemas, CLI changes, progress-file formats, or mass chapter-path churn. There is deliberately no `CHANGELOG.md`: the release body is the canonical history. Full convention, the pre-release checklist, and the release commands live in `docs/release-policy.md`.
