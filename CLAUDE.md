# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a Korean-language learning guide for becoming a Database Administrator (DBA). It is overwhelmingly Markdown content organized into a three-tier curriculum: `01-beginner` → `02-intermediate` → `03-advanced`, plus an `appendix/`. "Development" here mostly means writing and editing Markdown chapters.

The only executable code is a small set of **standard-library-only Python3 / Bash tools** — the runners live in `scripts/`, with their launchers and `install.sh` at the repo root — and there is no `pip`/`npm`/build system. Keep it that way: any new tooling must use only the Python standard library (no external packages). CI is a single workflow, `.github/workflows/tests.yml`, which runs `python3 -m unittest discover -s tests` on main pushes and PRs (ubuntu × Python 3.9/3.13, macOS × bash 3.2) and **installs nothing from PyPI** — that constraint applies to CI too, so a linter job is a decision to re-open, not a free addition. It is deliberately scoped to `push: branches: [main]`: `generate-branch.sh` copies main's whole tree onto the vendor branches, so the workflow file rides along and an unfiltered trigger would re-run the same tests three more times per regeneration. `./shoot doctor` is deliberately *not* in CI — it needs docker and a DB client, and the stage-definition parsing it was on the release checklist for is already covered by `ShippedStagesTest`. **The macOS runner has no docker**, which makes it the only place a test that leaks the ambient docker installation shows up: a test calling `cmd_doctor()` must pin `docker` in its own `shutil.which` fake (and stub `subprocess.run` for it), or its exit code silently becomes a property of the machine — that is exactly how `ClientCheckSymmetryTest` passed everywhere for months and failed the first time CI ran it on macOS. Current tools:
- `install.sh` (repo root) — one-line installer: clones into `${XDG_DATA_HOME:-~/.local/share}/dba-guide`, checks out the **latest release tag** (never `main` HEAD — CI runs the tests, but only tagged commits have had their *content* hand-checked), and symlinks `guide`/`exam`/`shoot` into `~/.local/bin`. Same script handles update (re-run, idempotent) and removal (`--uninstall`, plus `--purge` to delete the tree). Three rules it must never break: (1) it refuses to touch anything it did not create — ownership is decided by `is_our_install` (the path must be a repository **root**, checked via `--show-toplevel` rather than `--is-inside-work-tree` so a git-managed `$HOME` does not make every subdirectory look like ours, **and** hold `scripts/guide.py`, so a different repository parked at the install path is rejected too), and a foreign file at a launcher name, a non-directory at the install path, or tracked local modifications each stop the run; (2) `--uninstall` keeps the directory, because `.exam-results/` and `.shooting-progress/notes/` are gitignored and have no other copy — `--purge` deletes it only after printing what would be lost and reading a confirmation, and **refuses outright without a tty**, since the documented `curl | bash` pipeline cannot answer; (3) run from inside a clone it links in place and **never moves HEAD**, so a contributor's branch does not get detached onto a tag. `INSTALL_DIR` starts as a computation over the ambient `XDG_DATA_HOME`, which by itself remembers nothing — install with a custom value, update without it, and the script would target the default path, clone a second install, repoint the launcher links at it, and leave `--purge` deleting the wrong tree (all measured before the fix). `adopt_recorded_install` closes that by reading `STATE_FILE` (`${XDG_STATE_HOME:-~/.local/state}/dba-guide/install-path`), re-verifying it with `is_our_install`, and overriding `INSTALL_DIR` — announcing the substitution rather than making it silently. The contract is **an explicit `XDG_DATA_HOME` wins, an absent one is remembered**: adoption is skipped outright when the variable is set — tested with `[ -n "${XDG_DATA_HOME:-}" ]`, **not** `+x`, because `INSTALL_DIR` is computed with `:-` and the two must agree: under `+x` an empty exported value counts as an explicit destination while the path falls back to the default, so anyone with `export XDG_DATA_HOME=` in their rc loses the record — because a record that outranks an explicit destination leaves no way to relocate — a plain `--uninstall` keeps the record, so the reinstall gets pulled back, and the only remaining escape is `--purge`, i.e. destroying the one-of-a-kind learning records to move an install. Four rules hold this together. **(a) The record comes from `record_install`, never from the launcher links** — links say where we pointed, not what we created, and an in-place install points them at a contributor's own clone, so adopting from links let a later managed run `checkout --detach` that clone (measured: branch detached onto the tag, unpushed working file gone) and would have let `--purge` delete it; only `install_managed` records. **(b) Recording is bookkeeping and must never fail an install** — it runs the moment the clone lands, so neither a launcher-name conflict nor a missing release tag can leave a tree we made unrecorded, and its failures degrade to a warning instead of aborting a finished install under `set -e`. **(c) The record is untrusted input**, re-checked with `is_our_install` wherever it selects a target (the purge path reads it only to decide whether a stale record should go, and needs no such check). Note what that check is *not*: `is_our_install` (repo root + `scripts/guide.py`) is satisfied by a contributor's own clone, so it is a sanity check, not proof of authorship — and **do not try to infer authorship from git state.** Three attempts on this branch each replaced one proxy with another (launcher links, then the record, then "HEAD is detached"), and each new proxy was adopted without enumerating the states the world actually produces for it: links point at in-place clones, and detached HEADs come from submodules, worktrees, `clone --branch <tag>`, a bisect, a maintainer checking out a tag — while `install_managed`'s own early-return path leaves a fresh install **on a branch** whenever the newest tag sits at `main`'s tip, so a "detached means ours" guard refused installs the script itself had made. A missing record simply means no record; the correct response is the pre-existing behaviour (use the computed path), never an accusation. What keeps that honest is the companion rule: **`record_install` is called from exactly one place — immediately after `git clone` succeeds.** Recording later would let a run that dies in between leave a tree we made unrecorded forever. A record is a claim of authorship, and attaching it to a tree that was already there turns one mistake into a permanent aim point — point `XDG_DATA_HOME` once at a parent holding your own clone and, if that path were recorded, every later bare run would re-fetch and re-detach it and a bare `--uninstall --purge` would delete it. Recording only what we cloned holds the accepted residual risk to what v1.3.0 had: that one run fetches and detaches the tree the user named, and nothing after it does. The cost is that an install this script did not clone is never remembered — including a pre-v1.3.0 custom-path install, whose owner keeps passing the variable on **every** command, removal included, exactly as before. `install_managed` says so on screen when the location differs from what is recorded (`record_names`, not "does a record exist" — the record survives from the first install, so the file-existence form went silent for every returning user, which is exactly who needed telling), and stays quiet when the variable merely names the default, where the advice would be inert. Silence there let a later bare `--uninstall` strip the launcher links — the last pointer to that tree — while reporting success. The `fresh` flag gates both that notice and the "이미 최신입니다" line, which a just-cloned tree would otherwise print because a release-day tag sits at `main`'s tip. `INSTALL_DIR` is made absolute at definition for the same class of reason: normalizing only the record left the links relative to `~/.local/bin`, which killed all three launchers while the suite stayed green. `--purge` still guards deletion with `is_our_install` only, and refuses outright when the install path is a symlink, since `rm -rf` would remove the link and leave the tree while reporting success. Nothing in the tool may *suggest* aiming it at another tree — `warn_if_another_install_is_linked` names the other path and says this run installs elsewhere, and stops there. **(d) A plain `--uninstall` keeps the record** (it is the locator a later `--purge` needs once the links are gone); only a completed `--purge` removes it. When no record exists but a launcher link resolves to a valid install elsewhere, `warn_if_another_install_is_linked` says so and continues — it must not adopt (that is rule (a)) and must not stop, since a contributor running a managed install alongside their in-place clone looks identical. Right after a release the newest tag sits on `main`'s tip, so a just-cloned HEAD already equals that tag and takes the already-up-to-date branch  Must stay **bash 3.2 compatible** — macOS ships 3.2.57 and `curl | bash` uses it. Because it links the launchers, **`guide`/`exam`/`shoot` must each resolve their own symlink chain** before deriving `$here` — `${BASH_SOURCE[0]}` is the link's own path, not its target, so the naive `dirname` sends them looking for `~/.local/bin/scripts/*.py`. That shipped broken in v1.2.0 and was fixed in v1.2.1; `readlink -f` is not portable, hence the hand-rolled loop. Tests: `tests/test_install.py` runs the real script against a `file://` origin, copying it to a temp dir first (running the in-repo copy would make `BASH_SOURCE` trigger in-place mode and void every managed-mode test). Its fixture copies the **real** launchers rather than stubbing them, and `LinkedCommandTest` **executes the installed command through its symlink** — asserting `os.readlink` alone is what let v1.2.0 ship with all three commands broken.
- `scripts/generate-branch.sh` + `scripts/filter_dbms.py` — single-vendor branch generation (see below). Tests: `tests/test_generate_branch.py` runs the **real** script against a throwaway repo built in a temp dir. Unlike `test_install.py` it must **not** copy the script — `script_dir` comes from `${BASH_SOURCE[0]}` (to find `filter_dbms.py`) while `repo_root` comes from `git rev-parse --show-toplevel` in the cwd, so running the in-repo copy with the fixture as cwd already isolates the target. Two behaviours that surprise: `git worktree add -B "$target" main` resets the vendor branch to main on **every** run, so a regeneration never accumulates history (it is always main + exactly one commit — which is why the release docs expect `push --force-with-lease`), and the "no changes after filtering" branch is therefore reachable only when *nothing* in the tree is marked, not on a second run. Fixtures write their own markers inline, so unlike `test_reading.py` these tests need no vendor-branch `skipTest`.
- `scripts/check_content.py` — the mechanically-decidable half of the release checklist: relative links resolve, no tier/appendix document is missing from `README.md`, every chapter carries the four sections **in order**, every chapter has an `exams/<tier>/<stem>.json`. The section check also runs against the **three single-vendor views** (`--dbms`, or the `ShippedContentTest` assertion that covers all three): a section wholly inside one vendor's markers disappears from the other two branches while `main` still looks correct — that is how #90 survived to v1.4.0. The filter is `filter_dbms.filter_lines`, the same function `generate-branch.sh` uses, so the check cannot drift from the branches it stands for. Run it directly (`python3 scripts/check_content.py`, exit 1 on violations) for a line-per-problem report; in CI it rides the suite via `ShippedContentTest` rather than a separate workflow step, for the same reason `./shoot doctor` is not a step. Two things it deliberately does not do: it never guesses whether a *new* command belongs in a cheatsheet or a *new* term in the glossary (that needs reading the prose, and a token-scraping approximation false-positives until someone turns the checker off), and it skips links inside code fences, which are illustrative. The section check encodes the convention **as practised**, which is looser than the prose above: a `## 1. ` numbering prefix is optional, a subtitle may follow the name (`## 실습 예제 — PostgreSQL PITR`), concept chapters may say `주요 개념/문법` instead of `주요 명령어/문법`, extra sections may sit between the four, and `00-overview.md` plus `*-commands-cheatsheet.md` are exempt. `ShippedContentTest` skips the structure assertion on vendor branches: a section wholly inside one vendor's markers vanishes from the other two views, so the shape is only guaranteed on `main`. That skip is not a blind spot: the vendor-view assertions run on `main`, which is the only branch CI triggers on anyway.
- `guide` (repo-root launcher) + `scripts/guide.py` — top-level menu that offers the three runners below and hands off to them. **`MODES` order is the learning order** — read → check → experience (`read`, `exam`, `shoot`) — so the first row is the starting point offered to someone who has read nothing yet; `README.md` states the same sequence in prose, and `ModeTableTest` pins it. Wire-up tests locate a mode by key rather than index, so reordering does not break them. It only wraps: picking a mode drops out of curses and calls `exam.main([])`, `shooting.main([])`, or `reading.main([])`, then returns to the menu. It must catch `SystemExit` (exam.main raises it wherever it gives up, and reading.main propagates it unchanged from its own chapter→exam handoff) and `KeyboardInterrupt` (shooting.main does not catch its own) — otherwise finishing one mode kills the launcher. Run `./guide` with no arguments; `./exam` and `./shoot` remain the way to pass flags. The third mode is `scripts/reading.py`: DBMS → tier → chapter, body rendered by `scripts/markdown_render.py` before it is handed to `$PAGER`, then straight back to the chapter list — `x` on that list starts the highlighted chapter's bank, and the list labels carry `[시험 없음]` / `[지난 최고 …]` so you can see which chapters have one. It used to ask `[Y/n]` after every chapter instead; that prompt defaulted to yes, so the reflexive Enter that dismissed the old pause started an exam, and `Esc`/`q` did nothing in it — the same dead-end shape issue #95 fixed elsewhere. Vendor filtering calls `filter_dbms.filter_lines`, the same function `generate-branch.sh` uses, so the in-place view and the single-vendor branches cannot drift.
- `exam` (repo-root launcher) + `scripts/exam.py` — TUI learning-check quiz/exam runner (curses, line-mode fallback). Run `./exam` with no args to pick DBMS → tier → chapter interactively in the TUI; CLI args (a bank path/tier, `--dbms`, `--shuffle`) still work and skip the matching selection screen. `scripts/seed_exam.py` — generates draft question banks from a chapter. Question banks live in `exams/<tier>/<chapter>.json`. Tests: `python3 -m unittest discover -s tests`. Full convention: `docs/exam-authoring.md`. When adding or substantially changing a chapter, update (or regenerate + refine) the matching `exams/**/*.json` so the quiz stays in sync; keep chapter-specific commands as `short` questions tagged with the right `dbms`. `exam_bank_for(chapter_rel)` maps a chapter path to its bank (`exams/<tier>/<name>.json`, None when there is none) and lives here because both the shooting clear screen and the chapter reader need the same mapping. **`resolve_targets` must stay independent of the working directory** — it tries the argument as given, then under `REPO_ROOT`, then under `EXAMS_DIR`, so every form README documents works from anywhere. Until v1.3.0 the `.json` branch checked only the path as given: `exam exams/<tier>/<name>.json` worked solely with the repo as `cwd` (so no installed user could use it) and `exam <tier>/<name>.json` had never worked at all, since the `exams/` fallback existed only on the directory branch. Tier names resolve because the same-named chapter directory at the repo root holds no `*.json` and falls through. `ResolveTargetsTest` runs the documented forms from **inside and outside** the repo — a test that only ever runs at the repo root cannot see this class of bug, because `cwd` is a hidden input that is always correct there.
- `shoot` (repo-root launcher) + `scripts/shooting.py` — incident-response game runner. Injects real faults into a local Docker MySQL lab (`shooting/lab/compose.yaml`, containers `dbshoot-primary`/`dbshoot-replica`) and judges the player's recovery. Stages are declarative JSON in `shooting/stages/*.json`. Subcommands: `./shoot play | replay | up | down | doctor | notes` (`play` is the default), plus `--list`. Full convention: `docs/shooting-game.md`. **Any path this file prints for the user to paste must be absolute** — `COMPOSE_FILE`, not `shooting/lab/compose.yaml`; the engine always passed it absolute, but the advice shown when the lab stalls was relative and only worked from the repo root, which an installed user is not standing in. Display-only labels may stay relative. Things to know before touching it: (1) judging rests on **user separation** — `dba` is the player (watched via `mysql.general_log`), `app` is engine-spawned fault sessions, `repl` is the replication account, `root@localhost` is the engine itself; (2) engine-spawned sessions **must** pass `mysql --no-defaults`, because the container's `/root/.my.cnf` outranks `MYSQL_PWD` and would silently break auth; (3) `state` objectives need `hold_seconds` or a transient blip clears the stage; (4) the command log is **per server** — it is read on every watched container, and `KILL` targets/culprit pids are `(target, pid)` pairs because pids collide across servers; (5) the engine's own log-truncation **must** carry `NO_BINLOG` (`SET SESSION sql_log_bin = 0`), or it replicates and wipes the replica's log mid-cycle, silently erasing everything the player did there — stage `sql` steps, by contrast, are meant to replicate; (6) load-generating stored procedures **must** be `SQL SECURITY INVOKER`, since a `DEFINER` procedure reports `processlist.user` as the definer (root) and makes `app` sessions invisible to session tracking and cleanup; (7) `DELIMITER` is line-oriented, so procedure-creating `sql` steps need real `\n` around it — and it must **not be the first thing** in the step, because the engine prepends `SET SESSION sql_log_off = 1; ` and would leave it mid-line (start such a step with `\n`); (8) the engine is **vendor-dispatched by `target`** — containers are vendor-specific (`primary`/`replica` → MySQL, `postgres` → PostgreSQL), so `db_query()`/`db_spawn()`/`read_player_commands()` branch internally and call sites never name a vendor; a stage sets `dbms` and `normalize_targets()` fills omitted `on`/`source` **once at load time** (resolving the default at each read site instead lets one missed `.get("on", "primary")` silently query the wrong server); (9) PostgreSQL judging has two holes MySQL doesn't — **parse errors never reach the watch source** (measured: semantic and permission errors do, `KILL 999999` doesn't) and `SELECT pg_terminate_backend(pid) FROM pg_stat_activity` sweeps without naming a pid, so `kill_precision` can't see it (use `forbidden_command`); (10) statements executed **inside a stored procedure never get their own row** in `events_statements_summary_by_digest` (only the outer `CALL` does), so a stage cannot use statement digests as its diagnostic path while load comes from a procedure — `SHOW PROCESSLIST` does show the inner statement; relatedly, what the load query *reads* decides the plan (a `COUNT(*)` answerable from the index yields a covering `type=index` scan, not the `key=NULL` fingerprint an implicit-conversion stage is teaching), so always run the screen the stage claims the player will see; (11) **never rebuild a terminal tool inside curses.** A hand-rolled SQL console (editor + pager + completion, 363 lines) was deleted after it proved worse than the real client on every axis and its keymap kept colliding with the game HUD. `run_in_terminal()` (`def_prog_mode` → `endwin` → subprocess → `reset_prog_mode`) is the one channel — the mysql client (`c`), `$EDITOR` for postmortem notes, and `$PAGER` for reading them all go through it. Judging is unaffected because it keys on the logged user, not the input path; (12) a `sessions` setup step can hand each spawned session `{{session_index}}` (0-based), but that name is usable **only inside that step's own `sql`** — validation rejects it anywhere else, because nowhere else does it get substituted, so the literal `{{session_index}}` would otherwise reach real SQL or the player's screen unrendered; and locking stages are **vendor-dispatched** on top of that — when several sessions target the same row, InnoDB queues waiters on one record-lock and reports the **lock holder** as blocker (so MySQL 1-3 can pile every victim onto the same row), but PostgreSQL serializes waiters on the same tuple via **tuple lock**, so `pg_blocking_pids` names a mid-chain waiter instead (measured: with 4 victims on one row, the culprit showed up in only one of the four blocked rows, and the last waiter's blockers didn't include the culprit at all) — so PostgreSQL locking stages must split victims by `{{session_index}}` onto distinct rows; (13) a stage's diagnostic mcq choices are **shuffled by that game's seed** — write the correct one at `answer: 0` per the `exam.py` authoring convention, and pin `shuffle: false` on any question where choice order itself carries meaning; (14) any new `tui.pick()` screen shown **while the lab is up** must pass `allow_quit=False`, or a `Q` press raises `tui.QuitApp` and strands the `dbshoot-*` containers — `shooting._pick_client_target` is the only such screen today.
- Postmortem notes live in `.shooting-progress/notes/<stage-id>/<stamp>-<rank>.md` (gitignored). `build_note()` fills only **observed facts** (timeline from `session["events"]`, wrong quiz answers, violations) and deliberately leaves root cause / 5 Whys / action items blank — filling those in is the exercise. That is why the stage `debrief` never appears in the draft: `append_debrief()` adds it to the file only **after** the editor exits (idempotent, guarded by `DEBRIEF_MARKER`), so the player writes blind but the archived note still holds their analysis next to the official answer. Giving up deliberately does **not** attach the debrief — otherwise quitting becomes the shortcut to the answer.
- `scripts/markdown_render.py` — renders a chapter's Markdown to ANSI-styled plain text; `reading.py` runs it before handing the body to `$PAGER`. **It is not a viewer** — it draws no screen, only transforms text, so the rule above ("never rebuild a terminal tool inside curses") still holds: scrolling and search stay with `less`. Internally it is three layers, `inline_spans` → `layout` → `paint`, and **the order is a contract** — attaching ANSI first would put `\x1b[1m` into the width calculation, breaking alignment and bleeding styles across line boundaries. Width is measured with `tui.cwidth`; the module does no I/O (`width` and `color` are arguments only). Whether colour is used is decided by `tui.pager_supports_color()`, which turns it off for an unknown pager (e.g. `PAGER=more`), `NO_COLOR`, a pipe, or `TERM=dumb`. Even with colour off, the **structural** improvements remain — alignment, indentation, `☐` — because colour and structure are deliberately separable; backticks and `**` are **deliberately left in place** when there is no colour, since removing the marker as well as the colour would remove the distinction entirely. Nesting depth for bullets is measured in 4-column bands, because the chapters mix 2-, 3- and 4-space indents and `len(indent)//2` would give one nesting level three different bullets. **The output is reflow-safe: no rendered line carries meaning in its line head**, because `less` keeps SGR attributes across a soft wrap but never redraws a leading glyph or a padding run on the continuation line — so anything encoded there is lost the moment the reader narrows the window. Three rules follow, and each has a test in `ReflowSafetyTest` naming its reason. (1) Code fences get a short language label and a 4-space indent, **not** a `┌─/│ /└─` box, and the code goes out **verbatim** — which makes fence bodies **the one exception to the width guarantee** (the old box hard-wrapped at the render width and cut real commands mid-token: measured 6% of code lines at 80 columns, 25% at 60, 49% at 40, so a command copied off the screen would not run). Fold them with `less`, not here. (2) Tables are **never squeezed**: `_emit_table` draws the aligned table only when the natural width fits and otherwise emits one card per row (`▸ title` + `  header: value`), because table natural widths run to a median of 130 columns — 36 of the 44 tables were being squeezed even at 80 — and `PostgreSQL` came out as `PostgreSQ`/`L` at 40. There is no column-compression code left; `_pad` and `_alignments` serve the aligned path only. (3) Headings **wrap rather than truncate**, carrying the heading style onto every wrapped line; that style is what separates a wrapped heading from body text, and with colour off the separation is weaker but a lost tail was worse. Horizontal rules stop at `_RULE_WIDTH` (24) instead of filling the width. One limit worth recording: several glyphs the renderer introduces (`─ │ ━ • · ◆`) are East Asian Ambiguous width, which `tui.cwidth` counts as 1 — in a terminal configured to render ambiguous glyphs as 2 columns (a setting some Korean and Japanese users enable), 256 rendered lines across the chapters exceed 80 columns (down from 853 before the reflow-safety work, since the width-filling rules and gutters that dominated that count are gone). This is not a regression (`cwidth` encodes that assumption repo-wide, and there is no portable way to detect the setting), but it is the known limit of the width guarantee. `▸ ◦ ☐ ☑` are Narrow and unaffected.
- `scripts/tui.py` — curses primitives (display width, safe drawing, key normalization) **shared by `exam.py` and `shooting.py`**. It takes `curses` as a parameter rather than importing it, so the width/wrap functions stay unit-testable. Put new terminal-drawing helpers here rather than duplicating them in either runner. **Before writing a "pick one from a vertical list" screen, use `pick()`** — that shape had drifted into three separate implementations before it was consolidated here, each re-solving the key-comparison trap below on its own. `pick()` takes an optional `actions` string of extra keys; pass one and the return value becomes `Picked(index, action)` instead of a bare int (`action` is `None` for a normal Enter/number selection, `None` return still means cancel, `Q` still raises `QuitApp`). The two return shapes are deliberate — a caller always knows whether it passed `actions`, and the alternative was a second picker, which is exactly the drift `pick()` was consolidated to end. Action keys are compared **case-preserved**, in the same spot the `Q` check lives, so `actions="x"` does not swallow `X`. **Key comparison trap:** `read_key(wide=False)` returns ints from `getch()` while `wide=True` returns strs from `get_wch()` — the same `q` is `113` in one mode and `"q"` in the other. Always compare through `key_char()`/`is_enter()`/`is_backspace()`; comparing raw values silently kills whichever representation you didn't handle. `pick()` has one more trap in the same family: it splits `q` from `Q` **before** folding to lowercase, because letter case is load-bearing there — the one place in the codebase where it is. (`exam.py` predates these helpers and compares with `ord()`, which is correct — leave it alone.) `pick()` raises `tui.QuitApp` — a `BaseException`, not an `Exception` — on uppercase `Q`, to end the whole app in one keystroke from any screen (issue #95). `BaseException` is deliberate: `shooting.py` wraps its screens in two `except Exception:` safety nets (`choose_stage`, `cmd_play`) that print a traceback and fall back to line mode, and an ordinary `Exception` would route a `Q` press through that net instead of quitting. Intermediate loops must **not** catch `QuitApp` — there are exactly three catch sites (`guide.main`, and the `__main__` blocks of `reading.py` and `shooting.py`); `guide.py`'s `__main__` block has no `except QuitApp` of its own on purpose — `main()` already catches it before returning, so a second catch in `__main__` would be unreachable code. `page_text()` (hand text to `$PAGER`, returns `(returncode, printed_inline)` — callers read `printed_inline`, not the return code, to decide whether `pause_after_output()` has any plain text left on screen worth protecting) and `pick_line()` (the plain-text twin of `pick()`) live here too — `pick_line` was consolidated from three runner-local copies for the same reason `pick` was, and the chapter reader would have made a fourth. `tui.py` therefore touches `os`/`subprocess`, which the width and key helpers do not.

## Content architecture

- **Progression is encoded in directory names, not just content.** `01-beginner/`, `02-intermediate/`, `03-advanced/` map to career stages (예비/신입 DBA → 실무 독립 수행 DBA → 시니어 DBA/DB 아키텍트). Each tier's `00-overview.md` states prerequisites and a checklist for graduating to the next tier — read it before adding or reordering chapters in that tier.
- **Chapters are numbered and vendor-neutral by design.** The guide deliberately avoids committing to one DBMS; every chapter (except `00-overview.md`) covers a concept once and gives commands for PostgreSQL, then MySQL, then Oracle (MSSQL where relevant) in that fixed order, calling out divergence only when the behavior differs meaningfully — not just syntax.
- **Every chapter file (except `00-overview.md`) follows the same four-section structure**, in this order:
  1. `## 핵심 개념 설명` — why the concept matters, when it comes up in practice
  2. `## 주요 명령어/문법` — commands/syntax, PostgreSQL → MySQL → Oracle
  3. `## 실습 예제` — a short scenario-driven walkthrough
  4. `## 체크리스트` — `- [ ]` checkbox list of what the reader should now be able to do
  New chapters must follow this exact section order and heading names so the guide reads consistently across tiers.
- **`00-overview.md` in each tier uses a different structure**: prerequisites / competencies gained / criteria (checklist) for moving to the next tier (the top-level advanced overview instead describes ongoing growth directions, since there is no tier after it).
- **Each tier ends with a `*-commands-cheatsheet.md`** — a single-page Markdown table summarizing that tier's commands across the three DBMSes. When adding a command to a chapter, add the corresponding row to that tier's cheatsheet.
- **`appendix/dbms-comparison-matrix.md`** is the cross-tier, cross-DBMS reference table (including cloud managed services — AWS/GCP/Azure) and **`appendix/glossary.md`** is the cross-tier term glossary. These are meant to be kept in sync with terms/commands introduced in any tier's chapters — when introducing a new term or command in a chapter, consider whether it belongs in one or both of these appendix files too.
- **`README.md`** is the table of contents and learning roadmap; every chapter file is linked from it by relative path. Adding, removing, or renaming a chapter file requires updating the corresponding row/link in `README.md`.
- **Single-vendor branches (`postgresql`/`mysql`/`oracle`) are auto-generated from `main`.** `main` stays vendor-neutral; DBMS-specific paragraphs/code blocks/checklist items can be wrapped in `<!-- dbms:postgresql -->...<!-- /dbms:postgresql -->` (and `mysql`/`oracle`) markers, and `scripts/generate-branch.sh <dbms>` filters them into a single-vendor view of a chapter. Never hand-edit content directly on those branches — regenerate from `main` instead. Cheatsheets and the appendix comparison/glossary files are intentionally left unmarked (they're comparison tables by design) and pass through unfiltered on every branch. Full convention and the per-chapter marking-progress tracker live in `docs/dbms-branch-strategy.md`.

## Working in this repository

- All content is written in Korean; keep new content in Korean, consistent with the rest of the guide.
- Preserve the chapter filename convention: two-digit prefix + kebab-case topic (e.g., `04-user-and-privilege-management.md`). The prefix determines reading order within a tier.
- Cross-references between chapters use relative Markdown links (e.g., `03-advanced/03-disaster-recovery.md` linking to `07-cloud-managed-db-advanced.md`); keep links relative to the repository root or the linking file, matching existing usage.
- **Releases are tagged on `main` only, and always go out as a GitHub draft first.** A draft release does not create the tag ref, so it stays fully reversible until published; the vendor branches never get tags because they are regenerated from `main` and any tag on them would be orphaned by the next regeneration. Version bumps follow SemVer read as "does anything outside this repo break" — chapter/stage/question-bank additions are MINOR even in bulk, and MAJOR is reserved for incompatible JSON schemas, CLI changes, progress-file formats, or mass chapter-path churn. There is deliberately no `CHANGELOG.md`: the release body is the canonical history. Full convention, the pre-release checklist, and the release commands live in `docs/release-policy.md`.
